# PlayPOP — 보안 · 안정성(신뢰성) 설계 보강

> **목적:** 백엔드/플랫폼의 **보안(Security)** 과 **안정성(Reliability)** 을 설계 차원에서 보강.
> **자매 문서:** 인프라=`~/.claude/plans/polished-singing-sunbeam.md` · 양립=`docs/PLATFORM_INTEGRATION_DESIGN.md` · 기능=`docs/GAME_BACKEND_DESIGN.md` · 구조=`docs/BACKEND_SYSTEM_ARCHITECTURE.md` · 구현계획=`docs/IMPLEMENTATION_PLAN.md`.
> **연결:** 본 문서의 항목들은 위 구현계획 P0~P3에 **체크리스트(§6)** 로 매핑된다.

---

## 0. 두 개의 큰 원칙

1. **보안 = "클라이언트는 적이다(서버 권위)".** 중요한 판단(잔액·보상·점수·결제)은 전부 서버. 클라가 보낸 값은 *입력*일 뿐 *진실*이 아니다.
2. **안정성 = "장애는 일어난다(우아한 열화)".** 의존(백엔드·DB·캐시)이 죽어도 게임은 가능한 한 계속된다(Local 폴백). 모든 쓰기는 **멱등·재시도 안전**.

## 2. 보안 설계 (영역별)

### 2.1 인증/인가 (AuthN/AuthZ)
- **JWT(RS256/EdDSA) + JWKS 회전.** 서명키는 Secret Manager, 공개키로 검증(게임서버·realtime 동일). 클라엔 비밀키 절대 없음.
- **익명 우선 → 소셜 링크.** 익명 디바이스 세션도 안정적 `user_id`. 토큰 **짧은 수명(예: 1h) + refresh**. 포털 핸드오프용 **단기 scoped 토큰**(분 단위).
- **최소 권한(RLS).** 클라는 자기 행만 read. 잔액/원장 write 는 서버 전용 역할(SECURITY DEFINER RPC). 관리자 권한 분리.
- **세션 보안.** 같은-origin은 쿠키 `HttpOnly·Secure·SameSite=Lax`. CSRF(상태변경은 토큰+Origin 검증).

### 2.2 입력/출력
- **경계 검증=zod.** 모든 요청 바디/쿼리/헤더 스키마 검증(과/부족 필드 거부). (현재 apps/api 에 zod 도입됨 — 라우트별 스키마 적용 예정.)
- **출력 인코딩.** 사용자 표시 문자열(닉네임 등) 이스케이프, 저장 시 정규화·길이 제한.
- **에러 마스킹.** 내부 오류·스택·스키마를 외부에 노출 금지(현재 표준 봉투가 `code/message`만 반환).

### 2.3 경제·치팅
- 모든 변경=서버 검증 + **멱등** + **서버시간** + **rate-limit** + 타당성(점수 vs 플레이시간/이동수).
- **append-only 원장**(잔액 in-place 수정 금지) → 감사·복구·이중지급 탐지.
- **PvP**: 서버 권위 재시뮬 + 결과 **HMAC 서명** → 백엔드는 서명 있을 때만 경제/랭킹 기록(인프라 문서 §10.6).
- **랭킹 게이트**: 점수는 `/scores/submit` 안티치트 통과 후에만 보드 진입. 비정상치 격리·플래그.

### 2.4 데이터/프라이버시
- **익명 우선 = 최소 PII.** 불필요 개인정보 수집 안 함.
- **전송 TLS + 저장 암호화(at rest).** 시크릿=Secret Manager(레포/클라에 금지).
- **테넌트 격리**: 모든 유저 테이블 `tenant` + RLS. 독립 게임은 자기 테넌트만.
- **컴플라이언스(한국 PIPA/글로벌 GDPR)**: **계정·데이터 삭제** 경로(참고: `D:\Dev\word_eng\supabase\functions\delete-account`), 동의/철회, 데이터 보존·파기 정책. 캐쥬얼이 아동 대상이면 연령 고지·아동보호(COPPA) 검토.

### 2.5 결제·광고 사기
- **IAP**: 클라 영수증 절대 신뢰 X → Apple/Google **서버 검증** + 멱등(영수증=키) + 환불 웹훅 회수.
- **보상형 광고**: **SSV(Server-Side Verification)** 토큰 검증 + 일일 캡 + 쿨다운(서버).

### 2.6 네트워크/API
- **HTTPS 전용**, HSTS, 보안 헤더(CSP/X-Content-Type-Options 등 — 정적/CDN 측).
- **CORS 허용목록**(와일드카드 금지) — 통합 origin·독립 앱 origin만.
- **rate-limit**(유저·IP·op별) + **WAF/Cloud Armor**(봇·DDoS) + 자동스케일.
- **감사 로그**(인증·결제·관리자 행위) 보존.

### 2.7 의존성/공급망
- **lockfile 커밋**, 버전 핀, 정기 `npm audit`/Dependabot. 새 의존성 도입 시 검토.
- ⚠️ **즉시 액션(§7)**: 이번 `npm install` 후 audit 경고(7건) 트리아지.

## 3. 안정성/신뢰성 설계

### 3.1 무상태·스케일·헬스
- API **무상태** → 수평 확장(동접 대응). **헬스(/health)·readiness·liveness** 분리. 오토스케일(부하 기준) + min/max 캡(DB 보호).

### 3.2 데이터베이스
- **커넥션 풀링(PgBouncer) 필수**(서버 다수 → 직결 고갈 방지).
- **HA + 자동 failover**, **읽기 복제**(읽기 분산), 쓰기 프라이머리 서울 고정.
- **백업 + PITR**(시점복구), **복구 리허설**(정기). RPO/RTO 목표 설정.
- **마이그레이션 안전**: expand→migrate→contract(무중단), 파괴적 변경 분리, 배포 전 마이그레이션.
- **트랜잭션 규율**: 지갑 변경은 단일 트랜잭션(원장+잔액), 경쟁은 `FOR UPDATE`/버전.

### 3.3 캐시·우아한 열화(Graceful Degradation)
- **Redis HA**. 캐시 다운 시 DB 폴백(성능↓·동작 유지). 캐시 무효화 규칙 명확.
- **Local 폴백(이미 설계·구현)**: 백엔드 불통이면 게임은 localStorage로 계속, 쓰기는 **멱등키로 큐잉** 후 복구 시 재전송(서버 우선).

### 3.4 멱등·재시도·타임아웃·서킷브레이커
- **멱등(구현됨)**: grant 백본이 같은 키 1회만(순차/동시). 프로덕션은 DB 유니크 제약으로 내구화.
- 외부 호출(IAP·푸시·SSV)에 **타임아웃 + 재시도(지수백오프) + 서킷브레이커**. 비핵심은 큐/아웃박스(Pub/Sub)로 비동기.

### 3.5 잡/크론(일일리셋 등)
- **멱등·재실행 안전**(중복 실행해도 1회 효과). at-least-once + dedupe, 실패시 **데드레터**. 일일리셋(KST 00시) 스파이크는 **클라 리셋시각 지터**로 평탄화.

### 3.6 관측(Observability)·SLO
- **메트릭(골든 시그널: 지연·트래픽·에러·포화) + 구조화 로그 + 트레이싱(OpenTelemetry) + Sentry.**
- **핵심 알람**: DB 풀 포화, 에러율, p99 지연, Redis 가용성, **CDN 캐시히트·에그레스 비용**, 잡 실패.
- **SLO/SLI + 에러버짓** 정의(예: API 가용성 99.9%, p99 < 300ms).

### 3.7 배포 안전·킬스위치
- **blue/green 또는 canary + 즉시 롤백.** 마이그레이션 선행.
- **피처플래그/킬스위치(리모트 컨피그)**: 문제 기능을 **재배포 없이** 끔(이벤트·상점·신기능). 점진 롤아웃.

### 3.8 부하·카오스·용량
- 출시 전 **부하 테스트**(목표 rps + 데일리리셋 스파이크), 주요 의존 **카오스 테스트**(DB/캐시 다운 시 폴백 확인), 용량 헤드룸 확보.

### 3.9 재해복구(DR)
- 멀티리전 읽기복제 준비(P3), 백업 오프사이트, 복구 절차 문서화(runbook), 정기 복구 훈련.

### 3.10 운영(Incident)
- 온콜·런북·포스트모템(비난 없는). 보안 사고 대응 절차(시크릿 유출 시 회전·영향분석).

### 3.11 장애 격리(Blast Radius) — "통합 백엔드 = 전체 다운" 방지
**우려:** 통합(공유) 백엔드면 에러 하나가 전체 서버·전 게임을 죽이지 않나?
**답:** 장애 유형별로 다르며, 격리 설계로 가둔다. **진짜 SPOF는 앱 서버가 아니라 공유 데이터 계층(DB·인증)** — 이는 마이크로서비스로 쪼개도 동일하게 공유하므로, 방어 초점은 "앱 분리"가 아니라 **데이터 HA + Local 폴백**이다.

| 장애 유형 | 전체 다운? | 방어 |
|---|---|---|
| ① 요청 1건 버그(예외) | ❌ | 에러 핸들러가 그 요청만 500(현 표준봉투). 프로세스·타 요청 무영향 |
| ② 인스턴스 크래시(OOM 등) | ❌ | **무상태 + N대 복제** + 헬스체크 + 오토스케일 → LB 우회, 상태 손실 0 |
| ③ 공유 의존성(DB/Redis) 다운 | ⚠️ **진짜 위험** | DB HA+failover+풀링, Redis HA+캐시폴백, **Local 폴백**(백엔드 불통이어도 게임은 localStorage로 계속, 쓰기 큐잉 후 복구 재전송) |
| ④ 나쁜 코드 배포 | ⚠️ | canary/blue-green + **즉시 롤백** + **킬스위치**(리모트컨피그로 기능만 끔) |
| ⑤ 모듈이 외부호출로 지연(IAP/푸시) | ⚠️ 전파 | **벌크헤드**(의존별 동시성 상한) + 타임아웃 + 서킷브레이커 + 비핵심 비동기 큐 |

**원칙:** ⓐ 모듈러 모놀리스 ≠ 서버 1대(복제+오토스케일). ⓑ **테넌트 격리**(한 게임 문제가 타 게임 오염/잠식 안 함 — RLS + per-tenant rate-limit). ⓒ **탈출구**: 위험·무거운 모듈만 떼어 분리 가능(모듈 경계가 그 준비). **실시간 PvP는 이미 별도 서비스(GKE)** 로 분리. ⓓ 마이크로서비스는 격리↑지만 운영복잡도·분산트랜잭션 폭증 → 캐쥬얼·린팀엔 "복제 모놀리스 + 위 격리기법"이 최적, 필요 시 점진 분리.

## 4. 현재(P0) 코드에 이미 반영된 것 vs 갭

| 항목 | 현재 P0 | 갭(다음) |
|---|---|---|
| 서버 권위 | grant 백본·인메모리 원장 | DB 원장+유니크 제약(내구 멱등) |
| 멱등성 | ✅ 순차/동시 1회(테스트) | DB 레벨 멱등(다중 인스턴스) |
| 에러 마스킹 | ✅ 표준 봉투(code/message) | 민감로그 분리·감사로그 |
| 인증 경계 | ✅ 미들웨어(`Bearer anon:<id>`) | **진짜 JWT(JWKS)·refresh** |
| 입력검증 | zod 도입됨 | 라우트별 스키마 적용 |
| 테넌트 격리 | ✅ 헤더 반영(인메모리) | DB RLS·정책 |
| 폴백 | ✅ Local 어댑터(백엔드 무관 동작) | 오프라인 큐+재동기 |
| rate-limit/WAF | ✗ | Cloud Armor·토큰버킷 |
| 관측/알람 | Fastify 로그만 | 메트릭·트레이싱·알람·SLO |
| DB 풀·백업·복제 | ✗(인메모리) | PgBouncer·PITR·replica |

## 5. 보안 ≠ 기능, **모든 단계의 횡단 관심사**

보안·안정성은 "나중에 추가"가 아니라 **각 기능에 같이 박는다**. 그래서 §6 체크리스트로 단계별 강제한다.

---

## 6. 단계별 체크리스트 (구현계획 P0~P3 매핑)

**P0 (기반):** ✅ 표준 에러봉투 · ✅ 인증 경계 · ✅ grant 멱등 · ✅ 테넌트 컨텍스트 · ✅ Local 폴백 · zod 도입 · lockfile.
**P1 (MVP):** 진짜 JWT(JWKS·refresh) · DB RLS + 유니크 멱등 · PgBouncer · 라우트별 zod · rate-limit · 점수 타당성 게이트 · 구조화 로그+기본 알람(DB풀·에러율) · 백업/PITR · 마이그레이션 무중단 · 킬스위치(리모트컨피그) · CORS 허용목록.
**P2 (성장):** IAP 서버검증+멱등+환불회수 · 광고 SSV+캡 · 계정·데이터 삭제(컴플라이언스) · 읽기복제 · 트레이싱·SLO/에러버짓 · canary 배포 · 부하 테스트.
**P3 (최종):** PvP 서버 재시뮬+결과 서명 · 이상탐지(멀티계정·승부조작) · 멀티리전 DR·복구훈련 · 카오스 테스트 · WAF 고도화 · 운영 런북·온콜.
