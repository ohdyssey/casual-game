# PlayPOP — 외부 공격 방어 구조 설계 (Defense-in-Depth)

> **목적:** 향후 서버 구축·서비스 시 **외부 공격(치팅·사기·봇·DDoS·탈취)** 을 어떤 **구조(계층)** 로 막을지의 설계.
> **자매 문서:** 영역별 통제 상세=`docs/SECURITY_RELIABILITY_DESIGN.md`(인증·입력·DB·운영·장애격리) ·
> 구조=`docs/BACKEND_SYSTEM_ARCHITECTURE.md` · 인프라=`~/.claude/plans/polished-singing-sunbeam.md`.
> 본 문서는 중복 대신 **계층 구조·게임 무결성(리플레이 검증)·현금성 리워드 사기 방어**에 집중한다.
> **상태:** 백엔드 빌드는 CEO 리뷰로 보류 중 — 본 문서는 설계 확정 + "지금 클라에 심어둘 seam"까지만 정의(§5).

---

## 0. 설계 전제 (구조를 결정하는 3가지 사실)

1. **웹 클라이언트는 100% 리버스 가능하다.** 난독화·안티디버깅은 시간 벌기일 뿐 방어가 아니다.
   → 구조적 결론: **클라에는 비밀이 없고, 서버가 모든 진실을 재계산·검증한다.**
2. **가장 값나가는 자산은 '현금성 리워드(CashPOP 다이아→환전)'다.** 일반 캐주얼 게임과 달리
   공격자에게 **직접적 금전 동기**가 있다 → 방어 예산의 중심은 게임 치팅이 아니라 **환전 파이프라인**.
3. **완벽 차단은 불가능하다.** 목표는 차단이 아니라 **"공격의 경제성 붕괴"** — 캡·홀드·심사로
   공격 1건당 기대수익 < 공격 비용이 되게 만든다.

|---|---|---|

## 2. 5계층 방어 구조 (핵심)

```
 공격자
   │
 ┌─▼──────────────────────────────────────────────────────────┐
 │ L1 경계(Edge)     Cloud CDN(정적 전담) + Cloud Armor        │
 │                   WAF·DDoS 흡수·봇 시그니처·IP/geo·rate     │
 ├────────────────────────────────────────────────────────────┤
 │ L2 신원(Identity) 익명 디바이스 → 단기 JWT + refresh 회전    │
 │                   토큰 재사용 탐지 · 고위험 행동 시 단계적 마찰│
 ├────────────────────────────────────────────────────────────┤
 │ L3 게임 무결성     서버 발급 seed → 클라 플레이 →            │
 │    (Integrity)    move log 제출 → **서버 리플레이 재검증**   │
 ├────────────────────────────────────────────────────────────┤
 │ L4 경제(Economy)  append-only 이중 원장 · 멱등 · 캡/쿨다운   │
 │    /사기 방어      **환전 게이트**(홀드·실명·그래프·수동심사) │
 ├────────────────────────────────────────────────────────────┤
 │ L5 탐지·대응       경제 이상탐지 대시보드 · 킬스위치 ·        │
 │    (Detect/Resp)  어뷰즈 스코어 · 소급 감사·회수(claw-back)  │
 └────────────────────────────────────────────────────────────┘
```

**원칙:** 각 계층은 아래 계층이 뚫린다고 가정하고 설계한다(심층 방어). L1~L2는 표준 구성이므로
자매 문서에 위임하고, 이 게임의 차별 지점인 **L3·L4** 를 아래에 상세 설계한다.

### L1 경계 — 요점만
- **정적(게임 빌드·에셋)과 동적(API)을 완전 분리.** 정적은 CDN이 전담(원본 직접 접근 차단),
  API 만 LB→Cloud Armor 를 거친다. DDoS 는 대부분 CDN 층에서 흡수 → **API 서버는 얇은 표면만 노출**.
- rate-limit 3단: IP(Armor) → 유저(토큰버킷) → 오퍼레이션별(보상류는 더 엄격).
- 관리자 콘솔은 **별도 오리진 + IP 허용목록 + 강한 인증(2FA)** — 공개 API 와 물리적으로 분리.

### L2 신원 — 요점만
- 익명 디바이스 계정 우선(가입 마찰 0) + **단기 access(≤1h) / refresh 회전 + 재사용 탐지**
  (탈취된 refresh 가 재사용되면 해당 세션 계보 전체 폐기).
- **단계적 마찰(progressive friction):** 평시엔 익명으로 충분. **환전 등 고위험 행동에서만**
  휴대폰 본인인증·계좌 실명 확인을 요구 → UX 손실을 위험 지점에만 국소화.

## 3. L3 게임 무결성 — 서버 리플레이 검증 (이 코드베이스의 구조적 강점)

솔리테어를 포함한 전 게임의 코어 로직이 **Phaser-free 순수 모듈**(`games/*/src/logic`)이고,
딜이 **결정적 시드**(`seededRng`) 기반이다. 이 두 성질 덕분에 **서버가 클라이언트 플레이를
그대로 재실행해 검증**할 수 있다 — 난독화 없이 치팅을 구조적으로 무력화하는 정석 설계.

```
① 플레이 시작:  클라 ──POST /session/start {level}──▶ 서버
                서버: {session_id, seed, exp} 발급(서명) + 기록
② 플레이:       클라는 서버 seed 로 딜 → 유저 입력을 move log 로 축적
                (탭 슬롯 id · 드로우 · 부스터 사용 — 이동당 수 바이트)
③ 결과 제출:    클라 ──POST /session/result {session_id, moves[], claim}──▶ 서버
④ 서버 검증:    같은 seed 로 deal → moves 를 순수 로직(playCard/drawStock/
                bankWildToStock/consumeBonusCard…)에 재적용 → 점수·클리어·보상 재계산
                ⑤ 재계산값 ≠ claim → 거부 + 어뷰즈 스코어 가산. 일치 → 원장 기록.
```

- **비용:** 한 판 ≈ 수십~수백 move × 순수 함수 재적용 = **마이크로초~밀리초급**.
  초기엔 전수 검증 가능, 규모가 커지면 "보상 큰 판·고위험 유저 전수 + 나머지 표본" 으로 전환.
- **동적 난이도(luck) 주의:** `drawStock(state, rng)` 의 러버밴딩 rng 도 **세션 seed 파생**으로
  결정화해야 서버 재현이 일치한다(클라 `Math.random` 사용 금지 — §5 seam).
- **휴리스틱 보강(리플레이 통과를 우회하는 봇 대비):** 최소 플레이 시간, 입력 간격 분포(사람은
  불규칙), 세션당/일일 판수 상한, 승률 이상치. 리플레이는 "불가능한 결과"를, 휴리스틱은
  "가능하지만 비인간적인 결과"를 잡는다.
- **랭킹 게이트:** 검증 통과 결과만 리더보드 진입(미검증 점수는 보류 풀에).

## 4. L4 경제·사기 방어 — 현금성 리워드(CashPOP) 파이프라인

**구조 원칙: "적립은 관대하게, 환전은 엄격하게."** 적립 단계에서 유저를 괴롭히지 않고,
돈이 실제로 나가는 **환전 게이트 한 곳에 방어를 집중**한다(오탐 비용도 이곳이 가장 싸다).

```
적립(P·다이아)                         환전(현금화)
──────────────                        ─────────────────────────────────
광고 SSV(서버 콜백만 신뢰)              ① T+N일 홀드(지연 정산) — 봇 적발 시간 확보
미션/게임 보상(L3 검증 경유)     ──▶    ② 실명 게이트(휴대폰·계좌 본인 확인, 1인 1계정)
일일 캡·쿨다운(유저·디바이스·IP)        ③ 그래프 탐지(디바이스·계좌·IP 클러스터=공장 적발)
append-only 원장 + 멱등                ④ 임계 초과 → 수동 심사 큐(사람 확인)
                                       ⑤ 지급 후에도 원장 소급 감사·회수(claw-back)
```

- **광고 보상 사기(리워드 앱 1순위 위협):** 클라 "광고 봤음" 신호는 무시하고 **광고 네트워크의
  서버-투-서버 SSV 콜백만** 지급 근거로. + 유저·디바이스·IP 일일 캡 + **eCPM 대비 지급 상한**
  (지급액이 광고 수익을 초과할 수 없게 — 경제성 붕괴 원칙의 직접 적용).
- **멀티계정 공장:** 단일 계정 탐지로는 못 잡는다 → **그래프 관점**(같은 디바이스 지문·수취
  계좌·IP 대역을 공유하는 계정 클러스터)으로 환전 시점에 일괄 홀드.
- **어뷰즈 스코어(등급별 대응):** 에뮬레이터/헤드리스 UA·루팅 신호·입력 엔트로피·활동 시간대
  패턴을 가중 합산 → 낮음=통과 / 중간=캡 축소·홀드 연장 / 높음=환전 정지+심사.
- **이중 통화 구조 유지:** 랭킹 포인트(P)와 환전 재화(💎)의 분리는 이미 설계됨 — P 는 공격당해도
  금전 손실이 없으므로 방어 등급을 낮게, 💎 발행 경로만 고강도로.

## 5. 탐지·대응(L5) 및 지금 심어둘 seam (Phase A)

**L5 요점:** 경제 대시보드(시간당 발행/소각 총량·신규계정 환전 비율·상위 이상치 알람) ·
기능별 독립 킬스위치(환전/광고보상/이벤트 — 재배포 없이 차단) · append-only 원장 기반
소급 감사 + 회수 절차 런북. *(관측 스택·알람 상세는 자매 문서 §3.6~3.10.)*

**백엔드 보류 중에도 지금(클라만으로) 준비해 둘 seam — 비용 ≈ 0:**

| Seam | 현재 코드 | 준비 내용 |
|---|---|---|
| 시드 주입 | `PlayScene` `seededRng(level*7919+…)` 하드코딩 | 딜 시드를 **파라미터로 주입 가능**하게(기본=현행) → 후일 서버 발급 seed 교체가 한 줄 |
| 럭 rng 결정화 | `drawStock` 에 `Math.random` 전달 | 세션 seed 파생 rng 로 교체(서버 재현 일치의 전제) |
| Move log | `pushHistory`(undo 용) 존재 | 경량 이동 로그(슬롯 id·드로우·부스터) 축적 배열 추가 — 지금은 로컬 보관 |
| 경제 단일 경유 | liveops 지갑(localStorage) grant/spend | 재화 변경이 반드시 단일 함수 경유 유지(직접 쓰기 금지) — 서버 전환 시 이 함수만 교체 |
| 검증기 재사용 | `src/logic` 순수(Phaser-free) | 서버 착수 시 packages 로 호이스트 → **동일 코드로 서버 리플레이** |

## 6. 로드맵 (기존 P0~P3 에 얹는 보안 관점)

- **Phase A (지금, 클라):** §5 seam 5종. 서비스 동작 무변화.
- **Phase B (백엔드 착수):** L1(CDN/Armor)+L2(JWT) + 원장 + **세션 티켓/결과 제출 + 리플레이 검증**(전수).
- **Phase C (현금화 오픈 전 — 게이트 조건):** L4 전체(SSV·홀드·실명·그래프·수동심사) + L5 대시보드·킬스위치.
  ⛔ **이 계층 없이 환전 기능을 절대 오픈하지 않는다** — 리워드 앱의 사고는 곧 직접 금전 손실이다.
- **Phase D (규모):** 표본 검증 전환, 이상탐지 고도화(그래프·행동 모델), PvP 서버 재시뮬(기존 계획).

## 7. 명시적 비목표(하지 않을 것)

- **클라 난독화·안티디버깅 투자 안 함** — 웹에선 무력하고, 리플레이 검증이 이를 대체한다.
- **봇 100% 차단 시도 안 함** — 캡·홀드·심사로 공격 기대수익을 0 이하로 만드는 것이 목표.
- **적립 단계의 과도한 마찰 금지** — 본인인증 등 마찰은 환전 게이트에만.
