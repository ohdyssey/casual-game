## 2. 자산 3 / 갭 5

### ✅ 자산 — 서버 연결이 싼 이유

1. **쓰기 진입점이 3개뿐이다.** 모든 영속 변경이 `loadSave/updateSave/writeSave` 를 통과한다.
   네트워크 계층을 **이 모듈 뒤에** 넣으면 씬은 무변경이다.
2. **순수 로직이 난수를 주입받는다.** `createStairs(count, rng)` · `openPack(a,id,lv,rand)` ·
   `rollChestLoot(rand)` · `tickPvpBot(…, rng)` · `pickPlacement(…, {rng})` 가 전부 `Rng` 파라미터를 받는다.
   **같은 모듈을 서버에서 같은 시드로 돌리면 같은 결과**가 나온다 — 검증의 토대가 이미 깔려 있다.
   시드 RNG(`seededRng`, mulberry32)도 이미 있다.
3. **시간이 이미 파라미터다.** `periodIdFor(now: Date)` · `todayPeriodId(now)` 처럼 기간 판정 함수가
   `Date` 를 인자로 받는다. 서버 시간으로 갈아끼우는 일이 **호출부 치환**이지 로직 수술이 아니다.

### ⚠️ 갭 — 지금 상태로는 서버를 붙여도 의미가 없는 지점

| # | 갭 | 구체적 결과 |
|---|---|---|
| G1 | **지갑이 클라 권위** — `settleRun()` 이 보상을 계산하고 `updateSave({coins})` 로 직접 쓴다 | localStorage 한 줄 편집으로 코인 무한. 랭킹·리그·상점이 전부 무의미해진다 |
| G2 | **런이 재현 불가** — 코스가 `Math.random()` 으로 생성됨 | 서버가 "이 점수가 가능한가"를 판정할 방법이 없다. 점수 조작 = 무방비 |
| G3 | **기기 시계 신뢰** — 30곳의 `new Date()` | 시계를 돌리면 일일 보상·리그 정산·시즌을 반복 수확 |
| G4 | **단일 블롭 세이브** — 필드 단위 병합 없음 | 두 기기 = 마지막 쓴 쪽이 이김. 진행 손실이 조용히 발생 |
| G5 | **멱등성 없음** — 어떤 지급에도 키가 없다 | 재시도 한 번이 이중 지급. 오프라인 큐를 붙이는 순간 터진다 |

> **G1·G2 가 본질이다.** G3~G5 는 붙이면 해결되지만, G1·G2 는 *게임 코드의 구조*를 바꿔야 한다.

## 3. 상태 권위 분류 — 22필드를 누가 소유하는가

서버 연결의 90%는 "이 필드는 누구 말이 맞는가"를 정하는 일이다.

| 등급 | 뜻 | 충돌 시 |
|---|---|---|
| **S** 서버 권위 | 서버 원장이 진실. 클라는 캐시일 뿐 | 서버 값으로 덮어씀 |
| **V** 서버 검증 | 클라가 제출, 서버가 규칙으로 검증 후 확정 | 서버 판정 |
| **M** 단조 병합 | 양쪽 값 중 큰 쪽(줄어들지 않는 값) | `max()` |
| **C** 기기 소유 | 기기별 취향. 동기화하지 않거나 최신 기기 우선 | 최신 쓰기 |

| 필드 | 등급 | 근거 / 주의 |
|---|---|---|
| `coins` `gems` | **S** | 원장(ledger) 합계의 캐시. 클라가 **금액을 보내지 않는다** — 사유(reason)만 보낸다 |
| `items` | **S** | 소비 아이템 = 인벤토리. 구매·소모 모두 서버 |
| `ownedChars` `ownedPets` | **S** | 구매로만 늘어남 → 지갑과 같은 원장 |
| `album.cards/dust/packs/claimedPages/tradeTickets` | **S** | 팩 개봉 추첨이 서버여야 확률이 의미를 갖는다(§6) |
| `album.seasonId` | **S** | 시즌 경계는 서버 시간 |
| `totalSteps` | **V→M** | 런 검증 후 가산. 단조 증가라 병합은 `max` |
| `bestInfinite` `bestLevel` `bestThief` `bestSprint` `bestTimeAttack` | **V→M** | 랭킹에 들어가는 순간 검증 대상. TA 는 **작을수록 좋음**이라 `min` |
| `pvp.rating/wins/losses/streak` | **S** | 레이팅은 서버가 계산(상대 레이팅을 서버만 안다) |
| `pvp.recent` `pvp.recentScores` | **V** | 매칭 입력. 클라가 유리하게 조작할 동기가 있다 |
| `missionProgress` | **V** | 진척 팬아웃(상위 문서 §1-3)의 입력. 클라가 카운터를 올리지 않는다 |
| `missionClaimed` | **S** | 수령 = 지급 → 원장·멱등 |
| `league` | **S** | 기간 정산·순위는 서버. 지금 시드 봇은 §7 에서 실유저로 교체 |
| `today` `topEvent` | **S** | 기간·수령이 서버 시간에 묶임 |
| `level` | **파생** | `totalSteps` 에서 재계산 — **동기화 대상 아님**(이미 코드 주석에 명시됨) |
| `selectedChar` `selectedPet` `armedItems` | **C(+소유검증)** | 취향이지만 **보상 배수의 입력**이라, 정산 시 서버가 "정말 보유했는가"만 확인 |
| `settings` | **C** | 볼륨·진동·버튼반전 = 기기 취향. 동기화하면 오히려 성가시다 |

## 4. 클라이언트 구조 — `save.ts` 를 포트 뒤로

### 4-1. 왜 동기 API 를 유지하는가

`loadSave()` 는 **107곳**에서 동기로 불린다 — 렌더 도중에도 불린다. 이걸 `await` 로 바꾸면
씬 26개가 전부 비동기로 물들고, 그 과정에서 프레임 중간에 상태가 바뀌는 새로운 버그군이 생긴다.
**교체 대상은 API 가 아니라 그 뒤의 저장소다.**

```
                    ┌──────────────── 씬·UI (무변경, 107곳) ────────────────┐
                    │   loadSave()  ·  updateSave(patch)  ·  writeSave()    │
                    └───────────────────────┬───────────────────────────────┘
                                            │  (동기 유지)
                    ┌───────────────────────▼───────────────────────────────┐
                    │  save.ts  =  로컬 복제본(replica)  +  아웃박스(outbox) │
                    │   · 읽기: 항상 로컬 복제본 → 즉시 반환                  │
                    │   · 쓰기: 복제본 갱신 + 의도(intent)를 큐에 적재         │
                    └───────────────────────┬───────────────────────────────┘
                                            │  (비동기, 백그라운드)
                    ┌───────────────────────▼───────────────────────────────┐
                    │  sync 워커 — 멱등키 부착 · 재시도 · 서버 응답으로 복제본 조정 │
                    └───────────────────────┬───────────────────────────────┘
                                            ▼
                              @casual/core `platform` 포트 (이미 존재)
                              AuthPort · WalletPort · SavePort · ShopPort …
```

### 4-2. 핵심 개념 — "잔액"이 아니라 "의도"를 보낸다

지금: `updateSave({ coins: loadSave().coins + reward })` → **클라가 최종 금액을 정한다.**
바꿀 것: 클라는 `{ reason: 'run_settle', runId }` 를 보내고 **서버가 금액을 정한다.**

로컬 복제본은 **낙관적 예측치**를 즉시 반영해 화면이 멈추지 않게 하고, 서버 응답이 오면
그 값으로 **조정(reconcile)** 한다. 예측이 틀리면 화면의 코인이 한 번 튀는데, 그건
"서버가 진실"의 정상적인 대가다 — 숨기려 하면 이중 장부가 된다.

### 4-3. 이 게임이 `platform` 포트를 아직 안 쓴다

코어에 `PlatformContext`(Auth/Wallet/Save/Energy/Daily/Shop 포트 + `local` 어댑터)가 이미 있는데
펌프러시는 자체 `save.ts` 만 쓴다. **이관의 실체는 "save.ts 를 포트 어댑터로 다시 구현하는 것"** 이고,
`local` 어댑터가 지금 동작(전부 로컬)을 그대로 표현하므로 **오프라인·비로그인 모드가 공짜로 유지**된다.

## 5. 서버 계약 — 기존 자산과의 정합

`apps/api` 에 이미 있는 것(S0/S1 구현 완료, 테스트 25):

```
POST /api/v1/auth/anon      익명 식별
GET  /api/v1/profile
GET  /api/v1/save/pumpngo   ← 이 게임 네임스페이스가 이미 있다
PUT  /api/v1/save/pumpngo
GET  /api/v1/time           서버 시간
GET  /api/v1/wallet
POST /api/v1/wallet/grant   서버 권위 지급(멱등)
```

**즉 P0(식별·세이브·시간·지갑)의 서버 쪽은 이미 서 있다.** 이 게임이 안 붙어 있을 뿐이다.

### 이 게임 때문에 추가로 필요한 계약

| 엔드포인트 | 목적 | 왜 필요한가 |
|---|---|---|
| `POST /run/start` | 런 시작 → `{runId, seed, configVersion}` | G2 해소의 출발점. **코스 시드를 서버가 발급** |
| `POST /run/finish` | 런 결과 제출 → 검증된 보상 | 지갑 가산의 **유일한 경로**(단일 grant 파이프) |
| `POST /progress` | 진행 이벤트 팬아웃 | 미션·투데이·탑이벤트·앨범 진척을 **한 번에** 갱신 |
| `POST /pack/open` | 카드팩 개봉 | 추첨을 서버가 굴려야 확률·시즌 밸런스가 의미를 가짐 |
| `GET  /pvp/match` | 상대 기록 배급 | §7 — 지금 봇 자리에 **실유저 기록**을 꽂는다 |
| `GET  /config/pumpngo` | 리모트 컨피그 | 상점·확률·시즌·이벤트를 재배포 없이 |

## 6. 런 제출·검증 — 이 설계의 핵심

G2(재현 불가)를 푸는 방법은 세 단계로 나뉜다. **한 번에 3단계로 가지 않는다.**

### 단계 V1 — 개연성 검증 (싸고 즉시 가능)

서버가 런을 재현하지 않고 **불가능한 값만 거른다.**

- 경과 시간 대비 계단 수 상한 (연타 하한 110ms = `logic/autoPlay` MIN_TAP_MS → 초당 9칸이 물리 상한)
- 계단당 코인 기대값 대비 상한 (`logic/economySim` 이 이미 분포를 안다 — **시뮬레이터가 곧 검증기**)
- 모드별 규칙 (타임어택은 완주해야 기록 인정, 질주는 60초 고정 …)

이것만으로 "코인 999999" 류는 전부 막힌다. 정교한 조작은 못 막지만, **비용이 거의 0** 이다.

### 단계 V2 — 시드 고정 (구조 변경)

`POST /run/start` 가 `seed` 를 발급하고, 클라가 `createStairs(count, seededRng(seed))` 로 코스를 만든다.
그러면 **서버도 같은 코스를 안다.** 이 시점부터:

- 제출된 점수가 그 코스에서 도달 가능한 위치인지 확인 가능
- 특수돌·장식돌·코인 배치가 서버와 일치하는지 확인 가능 (`stonePlacement`·`pickupsFx` 규칙이 순수)
- 카드팩·보물주머니 추첨을 **서버에서** 굴려도 클라 연출과 어긋나지 않음

⚠️ **비용**: 36곳의 `Math.random()` 을 주입된 `rng` 로 바꿔야 한다. 대부분은 이미 `rng` 파라미터를
받는 함수에 `Math.random` 을 **기본값으로** 넘기고 있어서, 런 컨텍스트의 rng 를 위에서 내려주면 된다.

### 단계 V3 — 완전 리플레이 (마지막)

클라가 **입력 트레이스**(탭 시각 + 방향)를 제출하고, 서버가 같은 시드로 규칙을 재실행해
점수·코인을 스스로 계산한다. 클라가 보낸 숫자는 **참고도 하지 않는다**.

⚠️ **선결 조건 — 지금은 불가능하다.** 한 칸 이동의 규칙이 `scenes/play/stepper.ts` 에 있고
이 파일은 Phaser 씬에 묶여 있다. V3 을 하려면 **판정 규칙을 `logic/` 의 순수 모듈로 추출**해야 한다.
(`logic/jumpInput.ts` 가 이미 그렇게 분리된 선례다 — 같은 방식.)

> **✅ 확정(2026-08-18)**: 랭킹을 **명예 랭킹**으로 가기로 했으므로 **V1 + V2 가 종점**이다.
> V3 과 그 선결 조건(판정 규칙 순수 추출)은 로드맵에서 제외한다 — §10 결정 4.

## 7. 이 게임의 특수 사정 — 이미 서버 모양으로 만들어 둔 것

### PVP — 전적 기반 매칭 (2026-08-17 재설계)

PVP 를 **실시간이 아니라 전적 기반**으로 바꿔 두었다(`logic/pvpOpponent.ts`). 지금은 상대 기록을
*내 기록에서 역산해 합성*하지만, **서버가 붙으면 그 자리에 실유저 기록이 그대로 들어간다.**

```
지금:  내 recentScores → 기준선 → (합성) 상대 기록
서버:  내 recentScores → 기준선 → GET /pvp/match → 비슷한 기준선 유저들의 실제 기록 중 하나
```

봇 주행 로직(`tickPvpBot`)은 **목표 기록을 향해 사람처럼 오르는 연출**이므로 그대로 남는다.
즉 PVP 는 **실시간 서버가 필요 없다** — 기록 배급 엔드포인트 하나면 진짜 대전이 된다.
이게 이 게임에서 가장 값싼 서버 전환 지점이다.

### 리그 — 시드 고정 봇 → 실유저

`logic/league.ts` 의 `buildRoster(periodId, level)` 이 **periodId 해시로 봇 24명**을 만든다.
서버는 이 함수 자리에 같은 모양의 명단을 내려주면 된다(`{name, avatar, score}[]`).
**정산만 서버로 옮기고 로스터 계약은 유지**하면 UI 는 무변경이다.

### 카드 앨범 — 트레이딩만 백엔드 필수

설계서 `docs/CARD_ALBUM.md` §12 기준 **P0~P4 는 백엔드 없이 완결**되고 P5(유저 간 트레이딩)만 서버가 필요하다.
단 **팩 개봉 추첨은 서버로 올리는 게 맞다** — 시즌 밸런스(45일)가 확률에 걸려 있는데
클라 추첨이면 확률 자체가 신뢰의 대상이 아니다.

## 8. 오프라인 · 충돌 · 이관

### 오프라인은 선택이 아니다

캐주얼 게임은 지하철에서 켠다. **비행기 모드에서도 판이 돌아가야 한다.**
→ 로컬 복제본이 1급 시민이고, 서버는 *결국 일치시키는 쪽*이다.

| 상황 | 동작 |
|---|---|
| 오프라인 플레이 | 복제본에 낙관적 반영 + 아웃박스 적재. 화면은 평소와 동일 |
| 재접속 | 아웃박스를 **멱등키와 함께** 순서대로 전송 → 서버가 재계산 → 복제본 조정 |
| 조정 결과가 다름 | 지갑은 서버 값으로 덮고, 기록은 `max`(TA 는 `min`), 설정은 로컬 유지 |
| 아웃박스 폭주 | 런 단위로 병합(같은 runId 의 중복 제출은 서버가 멱등키로 흡수) |

### 멱등키 규칙

`{userId}:{runId}:{reason}` — 런 정산은 런당 1회, 미션 수령은 `{userId}:{missionId}:{periodId}`.
**키를 클라가 만들되 서버 DB 제약(UNIQUE)이 최종 방어선**이다(기존 apps/api 방침과 동일).

### 기존 유저 이관

라이브에 이미 로컬 진행이 있는 유저가 있다. 최초 로그인 시 **1회 업로드 후 서버 우선**으로 전환하되,
지갑은 **그대로 인정하지 않는다** — 검증 불가능한 잔액이기 때문이다.
권고: 이관 시점의 코인/젬을 **상한을 두고 인정**하고(예: 상위 1% 컷), 초과분은 메일박스로 보정 지급.
이 판단은 §10 의 열린 결정이다.

각 단계는 **그 자체로 출시 가능**해야 한다. 중간 상태에서 게임이 멈추면 안 된다.

| **P0 배선** | `save.ts` → 포트 어댑터 뒤로. `local` 어댑터로 **동작 무변경** 확인 | 523 테스트 통과 + 오프라인에서 기존과 100% 동일 | — |

## 11. 계정 설계 — 표준 모바일 로그인 (재제안)

### 11-1. "일반적인 모바일 게임 로그인" 의 실제 모양

첫 실행에 **로그인 화면**이 뜨고, 계정을 만든 뒤 게임에 들어간다. 국내 모바일 게임의 표준 구성:

```
┌─────────────────────────────┐
│         PUMP RUSH           │
│                             │
│   [ Google 로 계속하기 ]     │   ← Android 주력
│   [  Apple 로 계속하기 ]     │   ← iOS. 아래 ⚠️ 참조
│   [ 카카오로 계속하기 ]       │   ← 국내 편의(선택)
│   ─────────────────         │
│      게스트로 시작           │   ← 이탈 방어(선택)
│                             │
│  이용약관 · 개인정보처리방침   │
└─────────────────────────────┘
```

⚠️ **Apple 심사 요건(App Store 4.8)** — 제3자 소셜 로그인(Google·Kakao)을 제공하면
**Sign in with Apple 을 반드시 함께** 제공해야 한다. iOS 출시를 하는 순간 선택이 아니라 의무다.

⚠️ **개인정보 수집이 시작된다** — 소셜 로그인은 식별정보 수집이다. 개인정보처리방침·이용약관이
**출시 전 필수**가 된다. 선례가 이미 있다(`games/TICTACTOE/public/privacy.html`) — 같은 틀을 재사용한다.
만 14세 미만 처리(법정대리인 동의) 방침도 함께 정해야 한다.

### 11-2. 3안 비교

| | **A. 소셜 전용** | **B. 소셜 + 게스트** | **C. 게스트 우선(최초안)** |
|---|---|---|---|
| 첫 화면 | 로그인 강제 | 로그인 화면(게스트 포함) | 없음 — 바로 게임 |
| 첫 이탈 | **가장 큼** | 중간 | 가장 작음 |
| 계정 복구 | 항상 됨 | 소셜만 됨 | 연동 전엔 안 됨 |
| 연동 충돌 | **없음** | 게스트→소셜에서 발생 | 발생(가장 까다로움) |
| 서버 권위 | 0일차부터 | 0일차부터 | 연동 시점부터 |
| 구현량 | 중 | 중 | **가장 큼**(Keychain·복구코드·병합 UI) |

### 11-3. 권고 — **B안(소셜 + 게스트)**

> **Google · Apple 을 기본으로 두고, 게스트를 동등한 선택지로 남긴다. 카카오는 국내 지표를 보고 추가.**

- **A안을 권하지 않는 이유**: 캐주얼 게임의 첫 이탈은 로그인 화면에서 크게 난다. 광고로 유입된
  유저에게 로그인부터 요구하면 설치 비용이 그대로 샌다.
- **C안(최초안)을 권하지 않는 이유**: 구현량이 가장 큰데(Keychain·복구코드·병합) 얻는 게
  "첫 화면 없음" 하나다. 그마저 B안의 게스트 버튼이 대부분 흡수한다.
- **게스트를 "둘러보기" 로 격하하지 않는다** — 작게 숨기면 이탈 방어 효과가 없다. 다만 게스트는
  **재설치 시 진행이 사라진다**는 것을 버튼 옆에 한 줄로 명시한다(나중에 CS 로 돌아온다).

### 11-4. 게스트를 남기면 연동 충돌은 남는다 — 처리 규칙

게스트로 놀다 소셜 로그인을 눌렀는데 **그 소셜 계정에 이미 진행이 있는 경우.**

| 선택 | 결과 | 판단 |
|---|---|---|
| 기존 계정 이어하기 | 지금 게스트 진행 폐기 | 폐기 전 **명시 확인** — 되돌릴 수 없다 |
| 지금 진행 유지 | 소셜 계정 진행을 덮어씀 | 더 위험 — **기본값 금지** |
| 병합 | 기록 `max`, 지갑·컬렉션 합산 | ⛔ **제공하지 않는다** |

**병합을 빼는 이유**: 게스트 계정을 여러 개 키워 합치는 어뷰징 통로가 되고, 방어 비용이
기능 가치를 넘는다. 양쪽 요약(레벨·코인·앨범 진도)을 나란히 보여 주고 **둘 중 하나를 고르게** 한다.

### 11-5. 웹과 네이티브, 두 경로

이 게임은 **웹(ryanlogic.kr)에도 서비스 중**이다. 로그인은 두 경로를 다 지원해야 한다.

```
네이티브(Capacitor)              웹(브라우저)
  제공자 SDK → idToken            OAuth 리다이렉트 → code
        │                              │
        └──────────┬───────────────────┘
                   ▼
      POST /api/v1/auth/{provider}   ← 서버가 제공자에 검증
                   ▼
      provider identity → userId 매핑
                   ▼
      기존 issueToken() 그대로 (자체 세션 토큰 30일)
```

> **핵심**: 서버의 **토큰 발급·검증기는 그대로 쓴다**(`apps/api/src/lib/auth.ts`).
> 바뀌는 건 *신원의 출처*뿐이다 — `/auth/anon` 이 `/auth/{provider}` 로 늘어나는 형태다.
> 게임 클라이언트는 **어느 제공자로 로그인했는지 몰라도 된다** — 세션 토큰만 들고 있으면 된다.

### 11-6. 저장소 계층 — 이 결정과 무관하게 유지

코어의 `StoragePort` 는 **이미 비동기**다(`load(keys): Promise<…>`) — 네이티브 저장소가 비동기이기 때문.
반면 `loadSave()` 는 **동기**로 107곳에서 불린다.

> 로그인 방식을 무엇으로 정하든 **§4 의 "로컬 복제본" 은 필수**다. 모바일 셸로 가는 순간
> 동기 읽기가 불가능해지고, 메모리 복제본만이 그 간극을 메운다.

## 12-1. 인프라 스택 — Vercel+Supabase 로 갈 것인가 (2026-08-18)

### 결론

> **목적지 스택은 이미 정해져 있고 바꿀 이유가 없다** — `docs/RAID_META_INFRA_STACK_DESIGN.md` §2
> (Cloudflare + Cloud Run + Cloud SQL). 그 문서는 **Vercel 을 "현재 임시 — egress 한도·비용"** 으로
> 명시하고 배제했다. Supabase 는 **틱택토 실시간 대전 전용 예외 트랙**이고 이 게임에는 해당 없다.
>
> 다만 **지금 그 스택을 통째로 세우지도 않는다.** 유저 0명에 Cloud SQL HA + Memorystore 를 켜는 건
> 월 $800 을 태우는 일이다. **S0 → S1 → S2 로 나눠 올린다.**

### 왜 Vercel 이 목적지가 될 수 없나 — 근거 3가지

**① egress 가 이 게임의 지배 비용이다.**
배포본이 **67MB**(다이어트 후), 첫 세션 실제 전송이 약 **20MB**(CLAUDE.md 실측: 로비 도달 ~11MB + 플레이·지연 그룹).

| DAU | 월 전송량(추정) | Vercel(초과 종량) | Cloudflare |
|---|---|---|---|
| 1천 | ~0.2TB | 포함 범위 | $0 |
| 1만 | ~1.7TB | **~$100+/월** | **$0** |
| 10만 | ~17TB | **~$2,400/월** | **$0** |

Cloudflare 는 **egress 무료**다. DAU 10만에서 연 2,800만원 차이가 난다 — 이건 최적화로 좁힐 수 있는
격차가 아니라 **과금 모델 자체의 차이**다.
⚠️ 단가는 변한다 — 계약 전 반드시 현재 요금표로 재확인할 것.

**② `apps/api` 는 서버리스에 맞지 않는 모양이다.**
Fastify + kysely + `pg` 커넥션 풀 = **장수 프로세스** 전제. 서버리스에 얹으면 요청마다 커넥션이 뜨고,
Postgres 커넥션 고갈을 막으려 별도 풀러가 필요해진다.
실제로 이미 네 번 싸운 이력이 있다:

```
abc316a  tsconfig 를 자립형으로 — Vercel 이 상위 extends 를 따라가지 않는다
9573771  라우트를 Vercel 웹 표준 핸들러 형태로 — { fetch } 객체로 감싼다
a345249  공유 규칙을 상대경로 재노출로 — Vercel 이 TS 소스 import 를 남겨 죽는다
30a3461  마이그레이션의 없는 예외 조건명 수정 — 스크립트 전체가 롤백됐다
```

**모노레포 + 장수 서버**를 서버리스 플랫폼에 끼우는 비용을 이미 치렀다. Cloud Run 은 컨테이너라
이 마찰이 **구조적으로 없다**(로컬에서 돌던 Fastify 가 그대로 뜬다).

**③ Supabase 를 쓸 이유가 이 게임엔 약하다.**
Supabase 의 값어치는 Auth·Realtime·RLS 인데 — 인증은 **자체 토큰 발급기가 이미 있고**(`lib/auth.ts`),
실시간은 **PVP 를 전적 기반으로 만들어서 필요 없어졌다**(§7). 남는 건 관리형 Postgres 하나다.
그건 Supabase 여도 되고 Neon 이어도 되고 Cloud SQL 이어도 된다 — **DB 선택의 문제이지 플랫폼 선택이 아니다.**

### ⚠️ 정정 — 단계 구분에 두 축이 섞여 있었다 (2026-08-18)

처음 쓴 S0/S1/S2 는 **"플랫폼 선택"과 "인스턴스 사이징"을 한 축으로 뭉갰다.** 이 둘은 성질이 다르다.

| 축 | 단계적으로 갈 이유 | 판단 |
|---|---|---|
| **플랫폼**(어디에 배포하나) | 없음 — 옮기는 데 **비용이 든다** | **처음부터 목적지** |
| **사이징**(얼마나 크게) | 있음 — 안 쓰는 용량은 순수 낭비 | **단계적으로 키운다** |

**플랫폼을 단계적으로 갈 이유가 없는 이유:**

1. **비용 차이가 없다.** 목적지 스택의 S0 구성이 임시 구성과 같은 값이다(아래 표). Cloud Run 은
   요청이 없으면 0으로 내려가고 Cloudflare Pages 는 무료다. **아낄 게 없다.**
2. **API 는 아직 아무 데도 배포돼 있지 않다.** 즉 지금 정하는 건 "이관"이 아니라 **"첫 배포 위치"** 다.
   Vercel 에 먼저 올렸다가 옮기는 건 **순수 낭비**다.
3. **이관 비용의 증거가 이미 있다.** Vercel 에 API 를 얹으려다 네 번 고쳤다(위 §②). 임시로 올리면
   그 세금을 **두 번** 낸다 — 올릴 때 한 번, 걷어낼 때 한 번.
4. **개발 기간 내내 진짜 환경에서 돈다.** 플랫폼 특유의 문제(커넥션·콜드스타트·타임아웃·로그)를
   출시 직전이 아니라 **처음부터** 만난다.

### 최종 구성 — 플랫폼은 고정, 사이징만 성장

| | **처음부터(DAU ~1천)** | **성장(DAU 1만)** | **확장(DAU 10만 / 10k CCU)** |
|---|---|---|---|
| 정적·CDN | **Cloudflare Pages** $0 | 동일 $0~20 | 동일 $0~20 |
| API | **Cloud Run**(스케일 제로) $0~10 | 동일, 인스턴스↑ $30~80 | 동일 $100~300 |
| DB | **Cloud SQL** 최소(db-f1-micro) $10~25 | 소형 승격 $70~120 | HA + 리플리카 $200~500 |
| 컨테이너 레지스트리 | Artifact Registry ~$0.1 | ~$1 | ~$2 |
| 캐시·랭킹 | **없음** — Postgres 로 충분 | Upstash $0~15 | Memorystore $50~150 |
| 큐·분석 | 없음 | 최소 | Tasks/PubSub + BigQuery $20~80 |
| **합계** | **월 $10~35** | **월 $110~240** | **월 $800~1,200** |

> **세로줄이 안 바뀐다** — 서비스 목록은 처음부터 끝까지 같고, 숫자만 커진다.
> 이게 "처음부터 목적지"의 뜻이다. 마이그레이션이 로드맵에 없다.

## 13. 요약

- 이 게임은 **서버에 붙일 준비가 구조적으로는 되어 있다** — 쓰기 진입점 3개, 순수 로직 + rng 주입, 시간 파라미터화.
- 진짜 일은 **네트워크가 아니라 권위 이전**이다: 지갑(G1)과 런 재현(G2).
- **씬 코드는 고치지 않는다.** `save.ts` 뒤에 복제본+아웃박스를 넣는 것이 전체 설계의 축이다.
- PVP 를 전적 기반으로 바꿔 둔 덕에 **실시간 서버 없이도 진짜 대전**이 된다 — 가장 값싼 전환점.
- 출시 기준선은 **P0~P4**. P5·P6 은 경쟁에 보상이 걸린 뒤에 한다.
