캔버스를 **양축 가변**(세로가 하한에 닿으면 폭을 늘림)으로 산출해 FIT 검은 여백을 없앤다.
배경은 축소하지 않고 크롭/확장한다. 구현은 `@casual/core` 의 `designSize.ts`.

### 이 게임의 현재 상태 (2026-08-21)

| 항목 | 값 |
|---|---|
| 저작 폭 / 세이프존 | 1080 × 2400 (**항상 100% 보인다**) |
| 캔버스 폭 | **가변 1080 ~ 1350** (16:9 까지 여백 0) |
| 캔버스 높이 | **가변 2400 ~ 2600** (21:9 까지 여백 0) |

#### 구조 — 정렬은 **카메라**가, 가장자리 붙임만 **앵커**가

화면 요소가 두 갈래(에디터 저작 노드 + 코드로 그리는 HUD·팝업)라 각각 옮기면 반드시 빠뜨린다.
그래서 **카메라를 세이프존 원점으로 스크롤**해 한 번에 정렬한다 — 그 뒤로는 모든 코드가 예전처럼
저작 좌표(0..1080 × 0..2400)를 그대로 쓰면 된다.

| 모듈 | 역할 |
|---|---|
| `@casual/core` `safeZone.ts` | **정렬의 단일 지점**(전 게임 공통으로 승격) — `centerSafeZone`·`autoCoverBackgrounds`. game-shell 이 씬마다 자동 적용 |
| `logic/responsiveFrame.ts` | 이 게임의 좌표 계약 — 세이프존 상수·상한·앵커·팝업 배율 |
| `ui/safeZone.ts` | 코어 재수출(기존 import 경로 유지) |
| `ui/mainPins.ts` | 플레이 화면 노드 3그룹(아트 스택 / 하단 아이콘 / 상단 배너) 앵커 표 |
| `ui/layoutLoader.ts#anchorDoc` | 저작 문서에 세로 가장자리 앵커 적용(렌더 직전 1회) |
| `ui/overlay.ts` | 코드 오버레이 루트 + **캔버스 전체를 덮는** 딤 |
| `logic/homeStages.ts` | 홈 부지 스테이지 ↔ scrollX 유도(폭 종속 제거) |

#### 지켜야 할 것

- **`W`/`H` 는 캔버스가 아니라 저작 크기다.** 화면 전체를 덮는 것(딤·배경)은 `scene.scale.*` 또는
  `overlayScrim()` 을 쓸 것. 카메라 세로 계산은 `HomeScene.camH()`.
- **`min` 은 저작 크기 그대로**(늘리는 쪽으로만 가변). main.json 은 상단 헤더(y=744)·하단 아이콘
  (y=2213~2222)이 프레임 끝에 붙어 있어 min 을 낮추면 UI 가 잘린다.
- **보드는 세이프존 고정**(BOARD_LEFT 55 ~ BOARD_RIGHT 1025). 늘어난 폭을 보드가 먹으면 카드가
  커져 레벨 저작의 "editor px = game px" 1:1 계약과 커버 판정이 흔들린다.
- **패럴랙스(near-fixed) 레이어**는 카메라 스크롤을 factor 만큼만 따라가므로 `offset × (1−factor)`
  보정이 필요하다(하늘 0.02·원경 0.04 — 안 하면 16:9 우상단이 빈다).
- 화면비 회귀는 `npm run qa:play --viewport design|iphone15|iphonese|tall`.
- ⚠️ 이 게임은 코어의 **자동 중앙정렬을 끈다**(`autoCenterSafeZone: false`) — HomeScene 이 월드
  카메라를 직접 스크롤하기 때문이다. 씬들이 직접 건다(Play/Klondike/Load = 메인, Home = uiCam).

#### 노치·다이나믹 아일랜드 (2026-08-21)

아이폰은 화면 위아래를 시스템이 점유한다(아일랜드 59~62px · 홈 인디케이터 34px). 이 기기들은
화면비가 저희 가변 범위에 딱 맞아 **여백이 0** 이라, 상단 헤더가 아일랜드에 **100% 가려졌다**.

해결은 **카메라 줌**(코어 `safeZone.ts`). 캔버스 픽셀은 그대로 두고 줌만 낮춰 세이프존을 인셋
안쪽에 앉힌다 — **성능 비용 0**. 인셋이 없는 기기(안드로이드·데스크톱)는 줌 1 로 기존과 동일하다.

| 조건 | 줌 | 헤더 CSS 위치 |
|---|---|---|
| 인셋 없음 | 1.000 | 15~55 (기존과 동일) |
| iPhone 15 Pro Max | 0.900 | 72~109 ✅ |
| iPhone 16 Pro | 0.890 | 75~108 ✅ |

⚠️ **줌이 걸리면 "화면 전체"는 캔버스 크기가 아니다.** 딤·배경·앵커 계산은 전부
`viewBounds(scene)` 기준으로 바뀌었다 — `scale.width/height` 를 직접 �����지 말 것.
홈 화면은 월드 카메라에 자체 미세줌까지 겹치므로 `camW()`/`camH()` 를 쓴다.

⚠️ UI 전용 카메라(홈 `uiCam`)에 붙는 오버레이는 `overlayScrim(this, c, a, this.uiCam)` 처럼
**카메라를 넘겨야** 딤이 화면 전체를 덮는다.

⚠️ **공용 팝업 모듈**(entryPopup·collectionPopup·collectionHub·itemShop)도 마찬가지다 — `uiCam`
옵션으로 카메라를 넘긴다. 안 넘기면 메인(월드) 카메라 기준으로 계산되는데, 홈 화면은 월드 카메라가
팬·미세줌으로 움직이므로 딤이 어긋나 **상·좌·우·하 가장자리가 뚫린다**(실측: 노트8 1168×2400 에서
홈 진입팝업). 플레이 화면은 UI 카메라가 따로 없어 생략해도 된다.

검증: `?safeInset=59,0,34,0` 으로 실기기 없이 노치 조건 재현(진단 겸용).

#### 화면 회전 — **세로 유지가 기본**

가로로 돌렸을 때 "세로로 돌려주세요"를 띄울지는 `index.html` 의 미디어쿼리 하나로 갈린다.
판단 축은 **가로폭이 아니라 세로높이**다(펌프러시 2026-08-18 수정 이식).

```css
@media (orientation: landscape) and (max-height: 480px) and (pointer: coarse)
```

- **높이가 병목**이다 — 세로 저작이라 가로 화면의 렌더 폭 = 높이 × 0.45.
- 구 조건 `max-width: 1000px` 은 양방향으로 틀렸다: 폴더블 펼침(837×697)·소형 태블릿
  가로처럼 **높이가 넉넉한데도 안내가 떴고**(정사각에 가까워 돌려도 세로가 안 나온다 = 막다른 길),
  21:9 가로(1050×450)는 폭이 1000 을 넘어 안내가 **안 떴다**.
- `pointer: coarse` 필수 — 빼면 데스크톱에서 창을 좁히는 순간 게임이 사라진다(심사 반려 사유).
- viewport meta 에 `orientation=portrait` 도 함께 준다(비표준·보조 수단).

실측(8종): 폰 가로·21:9 가로 → 안내 / 폰 세로·폴드 펼침·iPad 세로·iPad 가로·소형 태블릿
가로·데스크톱 좁은 창 → **게임**.

⚠️ 태블릿은 **돌리라고 하지 않고 세로 화면을 그대로** 보여준다. 화면비가 낮아(iPad 세로 1.44)
필요 폭이 상한 1350 을 넘으므로 좌우에 여백이 남는다 — 의도된 동작이다(아래 참조).
JS `screen.orientation.lock()` 은 전체화면 + 안드로이드 한정이라 쓰지 않는다.

#### 넓은 폭에서 챙길 것 (2026-08-21 실측 수정)

- **암막 보드 패널(main.json layer_4)의 귀퉁이 라운드** — 저작 폭 1106 이라 캔버스가 넓어지면 네 귀퉁이가
  배경 위에 드러난다. 저작 radius 는 0 이라 직각으로 잘려 보인다 → `PlayScene.roundBoardPanelCorners()` 가
  **폭이 넓어졌을 때만** 같은 자리에 라운드로 다시 그린다(저작 폭과 같으면 손대지 않는다).
- **화면을 꽉 채워야 하는 것은 전부 `fullBleedBounds(scene)` / `overlayScrim()`** 으로 그린다 — 팝업 딤·
  코드 배경·그라디언트·암막. 저작 `W`/`H` 로 그리면 넓어진 좌우가 뚫려 **팝업이 전체 화면을 못 가린다**.

  ⚠️ **캔버스 크기(`scale.width/height`)로 그리는 것만으로는 부족하다.** 카메라가 세이프존 중앙정렬로
  `-오프셋`만큼 스크롤돼 있어, 원점(0,0)에서 시작하면 화면 **왼쪽에 오프셋만큼 띠가 남는다**
  (실측: 16:9 에서 좌 135px — 홈 데일리미션 팝업). 반드시 역오프셋이 적용된 헬퍼를 쓸 것.

  ⚠️ **고정 패딩도 안 된다.** 미션 결과 팝업은 저작 크기에 사방 90px 을 더해 그렸는데, 폭이 넓어지면
  좌우로 135px 씩 벌어져 모자랐다. 패딩은 `fullBleedBounds` 위에 얹을 것.

  적용 지점: 컬렉션 카드 연출 딤 · 미션 결과/상자 팝업 딤+입력차단 Zone · `drawBoardMask` ·
  `drawBackground`(Play/Klondike/Home) · 홈 데일리미션 딤 · LayoutPreview.

#### 상한을 더 올리려면

`MAX_W 1350` 은 **플레이 배경 크롭**이 정한 값이다. 배경은 cover 라 폭을 늘린 만큼 세로가 잘린다
(1350 에서 상하 각 300px · 주력 19.5:9 에서는 각 30px). 태블릿(4:3 → 1800)까지 덮으려면
**더 넓게 저작된 플레이 배경**(main.json layer_1, 현재 원본 841×1870)이 먼저 필요하다.

#### 가장자리 UI 밀어내기 — 기준은 **캔버스 상단** (2026-08-21 수정)

`ui/safeAreaUi.ts` 의 `topUiShift`/`bottomUiShift` 는 `frameInset`(= 세이프존 세로 중앙정렬로
생긴 여백)을 **더한 뒤** 침범량을 잰다. 저작 좌표만 보면 중복 반영된다 — 플립5(캔버스 2655)에서
이미 127px 내려와 있는 헤더를 107px 더 밀어 닫기 버튼과의 간격이 두 배가 됐다.
원본 규칙은 `packages/core/docs/RESPONSIVE_STANDARD.md` 13절.

## 텍스처 메모리 (필수) — 2026-08-27

아이폰 라이브에서 **실행 중 반복 크래시**가 났다(사파리 "…에서 문제가 반복적으로 발생했습니다").
JS 예외가 아니라 **웹콘텐츠 프로세스가 OS 에 죽는 것**이라 `__errors()`·healthMonitor 에 아무것도 안 남는다.
원인은 텍스처 메모리다 — 부팅에 업로드 이미지 397장을 전부 올려 **디코드 RGBA 317MB**였고,
iOS WKWebView 의 프로세스 한도(대략 200~400MB · 인앱 브라우저는 더 빡빡)를 넘겼다.

⚠️ **WebP 다이어트는 이 문제를 못 고친다.** 압축은 다운로드만 줄이고, 디코드된 RGBA 는 `가로×세로×4`
그대로다. **해상도를 줄이거나, 안 올리거나, 내리는 것** 셋뿐이다.

### 지금 걸려 있는 것 — 둘 다 **배포 시점**이라 런타임 동작은 안 바뀐다

| 층 | 무엇 | 어디 |
|---|---|---|
| ① 해상도 | 표시 크기 × 1.25 로 상한(기본 ×2 에서 하향) | `scripts/assemble-deploy.mjs` `DIET_TUNING.solitaire` |
| ① 해상도 | 저작 노드가 없는(=코드로 그리는) 아트의 표시 크기 | `diet-hints.json` (**계측으로 자동 생성**) |
| ② 미사용 제거 | 어디서도 안 쓰는 업로드는 배포본에서 삭제 | `unused-assets.json` |

실측(배포본 디코드 RGBA): **317MB → 부팅 156MB**(그룹 46MB는 예산 48MB로 제한 · 최악 총량 203MB).
`npm run check:budget` 이 한도(부팅 160MB / 총량 208MB)를 지킨다 — **넘으면 빌드가 먼저 실패한다.**

### 구조 — 부팅 메모리는 **카탈로그가 아니라 화면**에 비례해야 한다

해상도·미사용 정리는 **절편만 낮춘다**. `loadGameAssets` 가 매니페스트를 통째로 올리는 한
그림을 추가하면 **한 번도 안 보여줘도** 부팅 메모리가 는다(실측 장당 평균 607KB → +100장이면 +60MB).
그래서 화면 아트는 **그룹 단위로 상주**시킨다.

| 모듈 | 역할 |
|---|---|
| `scripts/gen-asset-groups.mjs` → `src/ui/generated/assetGroups.ts` | 화면별 키 묶음 + 최대 바이트(생성물) |
| `src/ui/assetBudget.ts` | 상주 예산·미리받기·LRU 해제·`openWithGroup` |
| `src/ui/loadingVeil.ts` | 못 맞췄을 때의 로딩 표시(180ms 넘을 때만) |
| `scripts/check-texture-budget.mjs` | **예산 게이트** — 넘으면 빌드 실패 |

- 부팅은 항상 보이는 것만 올린다. 그룹 키는 `assets.ts` 가 건너뛴다.
- 그룹은 두 종류다:
  · **레이아웃 그룹**(이벤트·리그·리더보드) — 저작 화면 단위. 눌러야 나온다.
  · **부�� 그룹**(office·bank·lot2) — 코드가 조립하는 타워 아트. 부지는 좌우로 늘어서 있고 화면엔
    **한 부지만** 보이므로, 그 부지가 필요할 때 받는다. 부지 1개 ≈ 10층 × 1.6MB ≈ 16MB 라
    부지를 늘려도 상주가 안 는다(전부 올리면 30층 95MB · 100층 316MB).
- ⚠️ **부지 그룹은 `ensure()` 뒤에 세워야 한다.** 아트가 없으면 건물이 조용히 안 그려진다
  (`buildOfficeTower`·`addCompetitiveFloor` 모두 텍스처 없으면 건너뛰는 방어가 있다).
  그리고 `buildOfficeTower` 는 **기존 오브젝트를 파괴하지 않으므로 두 번 부르면 겹쳐 쌓인다** — 1회만.
- ⚠️ 부지 그룹은 **서 있는 것**이라 LRU 축출에서 팝업보다 뒤로 민다(`STANDING_GROUPS`).
  팝업은 닫으면 그만이지만 부지는 내리면 건물이 사라진다.
- 화면 진입 전 한가할 때 `prefetch()` 로 미리 받는다 → **열 때 대기 0**(회귀에서 적중 확인).
- 상주가 `BUDGET_BYTES` 를 넘으면 **가장 오래 안 쓴 그룹부터** 내린다. 지금 화면이 쓰는 그룹은
  `pin()` 이라 안 내린다.

#### 지연이 느리다는 판단은 **헤드리스에서 하지 말 것**

실측(2026-08-27): 파일 21장 로드 **53ms** · GPU 업로드 **2ms** · Phaser 로더 = **파일 수와 무관하게
4~6프레임**. 60fps 면 ~85ms 다. 그런데 헤드리스는 5fps 라 같은 것이 **1.8초**로 보인다.
⚠️ 실제로 그 값을 실기기 속도로 오해해 이 설계를 한 번 통째로 철회했었다. 회귀 하네스
(`npm run qa:popups`)의 ms 는 **속도가 아니라 동작 여부**를 보는 값이다.

#### ⚠️ 그룹 로딩에서 실제로 터진 것 3가지 (2026-08-29)

"이벤트·리그를 누르면 로딩만 걸리고 화면이 안 뜬다"는 신고의 원인이 셋이었다. 전부 재발 방지 장치를 넣었다.

1. **로더 동시 요청 경합** — 그룹마다 곧장 로더를 건드렸다. 부팅 직후 미리받기 3개가 겹치면 두 번째부터
   `load.once('complete', run)` 으로 **앞 배치의 완료 이벤트 안에서** `load.start()` 를 불렀고, 그 시점
   로더 상태에서 시작이 씹혀 **완료 이벤트가 영영 안 왔다** → 프로미스 미해결 → 딤만 남았다.
   → `assetBudget` 이 그룹 로드를 **한 줄로 세운다**(`loadQueue`) + 완료 핸들러 안에서 바로 start 하지
   않고 한 틱 미룬다 + **8초 타임아웃**으로 어떤 경우에도 settle 한다.
2. **화면에 떠 있는 텍스처를 축출** — 예산을 맞추려고 부지 그룹까지 내렸다. 그 텍스처를 쓰던 오브젝트가
   남아 렌더러가 `glTexture` 가 null 인 것을 그리려다 예외를 던졌고, 그 프레임에서 루프가 끊겨 팝업이
   통째로 안 그려졌다. → **`STANDING_GROUPS`(부지)는 축출 후보에서 아예 제외**한다(순서만 뒤로 미루는
   것으로는 부족했다 — 예산이 모자라면 결국 내려갔다). **예산보다 화면이 우선**이다.
3. **그룹 크기를 원본으로 추정** — 다이어트 후 크기의 약 1.8배로 잡혀(82MB vs 46MB) 미리받기가 계속
   거부되고 열 때마다 과하게 축출했다. → 생성기가 **다이어트와 같은 규칙**으로 배포 후 크기를 계산한다.

⚠️ 회귀 하네스도 같이 고쳤다 — **딤과 팝업을 depth 로 구분**해서 센다(팝업 4300 · 로딩딤 4900).
  개수만 세면 **딤만 뜬 상태를 성공으로 읽어** 이 사고를 못 잡는다(실제로 못 잡았다).

#### 대기 구간에는 반드시 표시가 있어야 한다

미리받기를 못 맞춘 경우 짧은 대기가 생긴다. 그때 **아무 반응이 없으면 "안 열린다"로 읽힌다**
— 실제 신고를 받았다. `openWithGroup` 이 180ms 넘으면 `loadingVeil` 을 띄운다.
⚠️ 텍스처 해제(`textures.remove`)는 반드시 패널 `destroy()` 뒤에 — 먼저 하면 빈 사각형이 남는다.

### 표시 크기는 **손으로 적지 않고 잰다**

저작 노드가 없는 아트(코드가 `setDisplaySize` 로 그리는 것)의 표시 크기는 **게임에서 직접 계측**한다.
처음엔 손으로 19장을 적었는데, 사람이 유지해야 하고 표시 크기를 바꾸는 수정과 어긋난다.

```
npm run dev                            # 6209 띄워 두고
npm run measure:textures               # 홈·팝업을 돌며 실제로 그려진 최대 크기를 잰다 → texture-usage.json
npm run measure:textures -- --play     # 플레이 화면까지(⚠️헤드리스에서 잘 매달린다 — --headed 권장)
npm run gen:diet-hints                 # 그 값을 diet-hints.json 으로 굽는다
```

**계측이 실제로 무엇을 고쳤나(2026-08-27):** 메모리가 아니라 **화질**이었다. ×1.25 상한을 저작 노드
기준으로 잡았는데, 같은 아트를 코드가 노드보다 크게 그리는 경우가 **62장**이나 있었다
(컬렉션 카드: 저작 슬롯 134×203 → 보상 팝업 280×420). 그 키들은 필요 해상도의 40% 로 줄어
**흐려지고 있었다.** 계측 힌트가 이걸 되돌린다. 커버리지 39% 기준 메모리는 207MB 로 변화 없다 —
남은 절감은 커버리지를 넓혀야 나온다(미관측 214장).

- 계측기는 `src/ui/textureUsage.ts`(dev + `?measureTextures=1` 일 때만 — 운영 비용 0). 매 프레임 표시
  목록의 `getBounds()`(월드 AABB) 최대치를 키별로 남긴다. 월드 기준이라 **컨테이너 스케일·팝업 열림
  젤리 연출의 확대 피크까지** 포함된다.
- ⚠️ **한 번도 안 그려진 키는 새 힌트를 만들지 않는다.** 상한이 없으면 원본 그대로 나갈 뿐이지만,
  잘못 걸면 그 화면이 흐려진다. 수집기가 커버리지(관측/전체)를 찍으니 **낮으면 주행을 넓힐 것**.
- **힌트는 병합되고 줄지 않는다** — 이번 주행에서 안 그려진 키는 이전 값을 그대로 들고 오고
  (`diet-hints.json` 의 `_carried` 에 남는다), 계측치가 더 크면 그쪽으로 올린다.
  **작게 잡는 쪽이 유일하게 위험**하므로(그 아트가 흐려진다) 언제나 큰 쪽을 남긴다.
  `_carried` 가 줄지 않으면 그 화면을 `scripts/measure-textures.mjs` 의 돌아볼 목록에 넣는다.
- `texture-usage.json` 도 **누적**된다(최대치 유지) — 한 번에 모든 화면을 못 돌아도 여러 번 돌려 채운다.
- ⚠️ 헤드리스는 플레이 완주 중 잘 멈춘다(이 레포 공통 함정) — 수집기는 판을 **깔고 잠깐만** 돌린다.
  계측에 필요한 건 "그려졌는가"지 "이겼는가"가 아니다. 각 단계에 상한이 걸려 있다.

### 지켜야 할 것

- **표시 크기를 바꾸는 수정**(패널 `maxW`·버튼 `width`·`CARD_H_MAX` 등)을 했으면 **다시 계측**한다.
  힌트가 실제보다 작으면 그 아트가 흐려진다.
- 저작을 고쳤거나 화면을 새로 배선했으면 **`npm run gen:unused-assets`** 를 다시 굽고 diff 를 본다
  (**생성물이라 손으로 고치지 않는다**).
- ⚠️ **미사용 판정을 문자열 검색으로 하지 말 것.** 키는 런타임에 조립되는 것이 47종이나 된다
  (`up_Slitare_BG_${p}` · `up_Solirare_Officer_${pad2(level)}` …). 그래서 생성기가 템플릿 리터럴을
  정규식으로 바꿔 함께 본다 — 순진한 스캔은 살아 있는 파일 100MB 어치를 지우려 들었다.
- 현황 측정: 매니페스트를 돌며 `가로×세로×4` 를 더하면 된다(배포본은 `sharp(...).metadata()`).


## 레벨 3,000판 — 501부터는 **편집 복제** (2026-08-30)

PO: "레벨 상한 3천까지 저작. 난이도를 더 높일 필요는 없다. 기존 저작 내용을 편집하여 난이도를 유지."

`scripts/extend-levels.mts` 가 **321~500(180판)** 을 원본으로 **501~3000(2,500판)** 을 만든다.
2,500판을 새로 설계하는 것은 분량이 아니라 **검증**이 문제라(판마다 풀림·난이도를 다시 재야 한다),
**난이도가 수학적으로 보존되는 편집 두 가지만** 쓴다.

| 편집 | 왜 난이도가 그대로인가 |
|---|---|
| 좌우 반전 `x → 1080−x` | 커버는 **겹침 면적**으로만 정해진다 → 모든 x 를 뒤집어도 임의의 두 장의 겹침이 그대로라 **커버 그래프가 동일**하다. 인덱스도 안 바뀌어 해답 수순(`p<i>`)이 그대로 성립한다. |
| 랭크 회전·반사 `r→r+k` / `r→k−r` (mod 13) | 매칭이 **±1 순환**이라 차만 보면 된다. 회전은 차를 보존하고 반사는 부호만 뒤집는다(±1→∓1) — 어느 쪽도 "낼 수 있는 수"를 바꾸지 않는다. 특별 취급되는 랭크가 없어 안전하다. |

두 축이 직교해 원본 1판에서 **52가지**가 나온다. 반복은 14회뿐이라 **완전 중복 0**이다.

- ⚠️ **대상 레벨은 원본과 같은 페이스 위상이어야 한다.** 저작된 스톡 장수는 그 레벨의 페이스 목표
  (`paceCurve.paceTargetFor`)에 맞춰 튜닝된 값이다. 목표는 `(level−11)%6` 과 `(level−13)%9`
  (단 `level%10≠0`)로 정해지므로, 번호 차가 **90의 배수**면 세 조건이 전부 맞는다. 그래서 원본 구간
  길이를 90의 배수로 잡는다 — 스크립트의 `assertPhaseSafe` 가 강제한다. **여기를 어기면 판은 풀리지만
  난이도가 목표와 어긋난다**(조용히 틀리는 종류의 사고다).
- ⚠️ 원본 6판(355·388·391·409·454·472)이 **해답 수순 없이** 저작돼 있다. 그대로 두면 검증 불가능한 판이
  84개로 번져서, **같은 위상의 대체 원본(±90)** 으로 바꾼다. 1~500 의 15판은 원래 결함이라 그대로 둔다.
- 검증: `npx tsx scripts/replay-solutions.mts` 가 **엔진 규칙으로 전 레벨을 재생**한다 —
  실측 2026-08-30: 성공 2,985 · 실패 0 · 해답없음 15(전부 1~500 의 기존 결함).
- ⚠️ 팩이 **25.5MB** 가 됐다(대부분 들여쓰기). `vite.config.ts` 의 `minifyLevelPack` 이 **빌드 출력만**
  minify 한다(10.2MB · gzip 1.12MB). 원본은 카드 에디터가 pretty 로 다시 쓰므로 손대지 않는다.
- 부팅 JS 힙은 팩 파싱분 **+23MB**(실측). 텍스처 예산(부팅 156MB)과는 별도 계정이다.

| 모드 | **(1장 / 3장) × (일반 / 타임어택)** = 4가지, 홈에서 한 번의 탭으로 고른다 | `logic/bonusGame.ts` `BonusMode` + `timed` |

  안 그러면 그 문으로는 무제한이 된다. 씬의 `init()` 은 남은 판수를 **읽기만** 한다.
  (처음엔 init 에서 차감했는데, 결과 팝업의 '한 번 더'(같은 씬 재시작) 경로에서 **차감이 빠졌다** —
  Phaser 의 씬 재시작이 init 을 다시 도는지에 기대는 구조였다. 회귀가 잡았다.)
- **하단 버튼은 세 개다** — `🔄 다시하기`(**같은 판을 처음부터**) · `↩ 되돌리기` · `🎲 다른 판`(새로 섞기).
  나가는 길은 ✕·☰ 메뉴·결과 팝업에 있어 하단 줄을 쓰지 않는다(구 `🏠 나가기` 자리가 '다른 판'이 됐다).
  ⚠️ 새로 배분할 땐 `initialState` 도 함께 갱신한다 — 안 하면 '다시하기'가 화면에 없는 예전 판으로 간다.
- ⚠️ **'다시하기'·'다른 판'도 한 판을 쓴다**(PO 2026-08-30). 예전엔 공짜였는데, 공짜면 하루 2회가
  "이길 때까지 무제한"이 되어 이론상 보상이 무한이었다. 차감 지점은 `resetBoard()` 하나다(두 버튼
  공통) — **여기를 안 지나는 경로를 만들면 그 문으로는 공짜가 된다.**
  차감에 실패하면(코인 부족) **보드를 건드리지 않는다** — 돈만 빠지거나 판만 바뀌는 반쪽 상태 금지.
  타임어택 결과 팝업의 '같은 판 다시'도 마찬가지라, **차감 성공 뒤에 팝업을 닫는다**(먼저 닫으면
  코인이 모자랄 때 보드도 팝업도 없이 남는다).
- 이 게임은 **레벨 진행도·미션 별점을 건드리지 않는다**(레벨 체계 밖). 미션 배너는 읽기 전용 표시다.

  코드로 그린다. 아트(`up_Solitare_UI_BonusGame`)가 매니페스트에 들어오면 자동으로 그림이 바뀐다.
  **아트가 오면 저작으로 옮기는 것이 정답이다.**
- **3장 뽑기는 웨이스트 맨 위만 쓸 수 있어 훨씬 어렵다** — 그래서 보상이 두 배다.
  게임비·무료 판수는 **두 모드가 함께 쓴다**(어려운 쪽을 골랐다고 판을 더 주지 않는다).
  ⚠️ 모드는 씬 밖에서 오므로 `toBonusMode()` 로 접어 받는다 — 깨진 값이 어려운 판을 열지 않게.
  ⚠️ 딜은 `dealKlondikeForLevel(..., drawOverride)` 로 **모드가 장수를 정한다**. 예전 레벨 커브
  (`drawCountForLevel`)는 인자를 안 넘겼을 때의 폴백으로만 남는다.
### 탭 자동 배치 — **런째 승리패로** (2026-08-29)

컬럼 중간을 탭하면 그 지점부터 앞까지가 런으로 잡힌다(고전 규칙). 예전엔 이때 **파운데이션을 아예
보지 않았다**(`count !== 1` 이면 건너뜀) — 2장이 잡히면 무조건 태블로로만 갔다. 이제 `tryRunToFoundation`
이 **맨 앞부터 한 장씩** 올려 본다. 런은 색 엇갈림 내림차순이라(♥3 위 ♠2) 위에서부터가 곧 랭크
오름차순이 되어, 파운데이션이 받아 줄 수 있는 유일한 순서다.

- ⚠️ **전부 올라갈 때만 적용한다.** 앞 한 장만 올리고 나머지를 두면 "런째 옮긴다"는 조작 감각이 깨진다.
  일부만 가능하면 실패로 두고 태블로 자동 배치로 넘긴다.
- ⚠️ 되돌리기는 **이 이동 전체가 한 번**이다(`pushHistory` 1회) — 중간 상태로 돌아가지 않는다.

### 홈: 세이브 스냅샷을 오래 들고 있다 — **정산은 읽기 전에** (2026-08-30)

PO 신고 "어제 리그 5위 했다는게 계속 뜬다"의 정체는 **오래된 스냅샷 덮어쓰기**였다.

`HomeScene.create()` 는 앞머리에서 `const save = loadSave()` 로 스냅샷을 뜨고 **한참 뒤**
`writeSave(save)` 로 되쓴다. 그 사이에 `settleLeagueIfNeeded()` 가 세이브를 바꿨으니(기간 id·점수·
지급 코인) 되쓰기가 **정산 결과를 통째로 되돌렸다.** 그래서 홈에 들어올 때마다 같은 정산이 다시
일어나 같은 토스트가 계속 떴고, 헤더에 잠깐 보이던 보상 코인도 저장되지 않았다.

→ 정산을 **`loadSave()` 앞으로** 옮기고 결과만 `this.leagueSettled` 로 들고 다니다 화면이 선 뒤 알린다.

- ⚠️ **이 파일에서는 `loadSave()` 뒤에 세이브를 바꾸는 함수를 부르지 말 것.** 불러야 하면 스냅샷을
  다시 읽어야 한다. HomeScene 은 스냅샷 하나를 수백 줄에 걸쳐 들고 있어 특히 위험하다.
- 회귀: **`npm run qa:league`** — 보상 잔존 · 안내 1회 · 재진입 중복지급 없음.
- ⚠️ 회귀 하네스가 두 번 헛짚었다. ① 부팅 **전에** 세이브를 심으면 1회성 `resetEventsOnce` 가 리그
  점수를 먼저 비워 정산이 안 일어난다 → **부팅 뒤에** 심는다. ② 안내는 `delayedCall(900)` 인데
  **씬 시계는 `delta` 고정(16.67ms)** 이라 헤드리스 5fps 에서 900ms 가 실제 **~11초**다 → 넉넉히 기다린다.

### 안내는 **한 번만** (2026-08-30)

PO: "보상 받기나 튜토리얼에 대한 안내가 한번 출력된 후 계속 반복 출력되지 않도록."

  (실측: 3회 진입 = 3회 표시). 룰 안내(`showRules`)는 이미 `klondikeRules` 로 1회였다.
- ⚠️ 기록은 세이브가 아니라 **전용 키**(`save.ts` `TIPS_KEY`)에 남긴다 — 본 세이브에 넣으면 다른 곳의

- 보상 액수는 **홈 선택 팝업 버튼에 항상 적혀 있다** — 그래서 조합별이 아니라 통째로 한 번이면 충분하다.

### 승리 가능 보장 — **3장 뽑기가 구멍이었다** (2026-08-29)

딜은 무작위로 주지 않는다. 후보를 여러 개 깔아 **그리디 봇이 한 번이라도 이긴 딜만** 채택한다
(이긴 수순 = 승리 가능 증거). 이때 뽑기 장수도 **실제 모드 그대로** 놓고 잰다.

그런데 **3장 딜은 그리디가 승리를 증명해 내는 비율이 딜당 17%뿐**이다(1장은 훨씬 높다). 후보를
12개만 재던 예전 예산으로는 `0.83¹² ≈ 11%` 가 "증거 없음"이 되어, 난이도 통제도 승리 보장도 없는
최후 폴백으로 샜다 — 실측 lv150 3장 모드 **40판 중 4판**. PO 신고("못푸는 문제가 있다")의 정체다.

| | 폴백률(3장 lv150) | 평균 그리디 승률 |
|---|---|---|
| 수정 전 | 4/40 | 0.45 |
| 수정 후 | **0/60** (전체 0/360) | 0.60 |

- ⚠️ **`maxMeasured` 를 키우려고 `candidates` 를 같이 올리지 말 것.** 후보 *생성*은 나쁜 경우가
  아니라 **매번** 드는 선불 비용이다 — 24→48 로 올렸더니 딜 생성 p50 이 80ms→**323ms** 로 뛰었다.
  풀을 다 쓰고도 못 찾았을 때만 **그 자리에서 새로 깔며 이어서 재는** 확장 루프가 정답이다(공짜).
- 회귀: `klondikeDifficulty.test.ts` 의 "검증 안 된 딜이 나가지 않는다"(시드 고정 — 깨지면 예산이
  되돌아간 것이다).
- ⚠️ **난이도는 메인 레벨을 따라간다**(`floor(레벨/10)` = 회차). 보너스는 레벨 체계 밖인데도
  150레벨이면 최고 난이도 구간에 들어간다 — 의도인지 확인이 필요한 지점이다.

- **진 판의 게임비는 돌려주지 않는다**(PO "실패는 게임비 회수") — 차감이 시작 시점이라 결과와 무관하다.
- ⚠️ **보상은 배수가 아니라 표다**(PO 2026-08-30 개정). 예전엔 타임어택 = 일반 ×3 이었는데 개정값은
  배수로 안 떨어진다(3,000→5,000 = ×1.67 · 5,000→7,000 = ×1.4). **배수 상수를 되살리지 말 것.**
- ⚠️ 게임비 2,000 대비 **1장 일반의 순이익은 +1,000 뿐**이다 — 유료 판은 승률 50% 를 넘어야 본전이고,
  그 아래면 코인 싱크로 작동한다(예전 5,000 보상은 파셋이었다). 보상을 만질 땐 `BONUS_PAID_FEE` 와 함께 볼 것.
- 하루 2판은 **하드 제한이 아니라 무료 구간**이다 — 그 뒤로는 게임비를 내고 계속할 수 있고,
  코인이 모자랄 때만 막힌다. 화면(홈 배지·결과 팝업 버튼)이 **낼 금액을 먼저 보여 준다**.

### 타임어택 (2026-08-30)

같은 규칙에 **제한시간만** 얹은 변형이다. 뽑기 장수(1장/3장)는 *규칙*을, 제한시간은 *압박*을 바꾼다 —
성격이 달라 축을 둘로 두고 **곱집합 4가지**로 쓴다(4값 열거형으로 합치지 않는다).

- 홈 선택 팝업은 **2×2 격자**다 — 세로가 규칙, 가로가 압박. 어느 조합이든 **탭 한 번**으로 들어간다
  (PO "여러번 선택하지 않고 바로 접근 가능한 방식"). ⚠️ 조합을 늘리면 격자가 목록이 되어 이 성질이 깨진다.
- **'다시하기'·'다른 판'은 시계도 처음부터**(PO 2026-08-30). 게임비를 냈으니 새 판과 같은 조건이어야
  한다 — 남은 시간을 이어받으면 판만 새로 깔아 주고 사실상 못 푸는 판이 된다. 시간 초과 뒤
  '같은 판 다시'도 같은 길(`resetBoard` → `startTimeAttack`)을 지난다.
- ⚠️ `startTimeAttack()` 은 **여러 번 불린다**(진입·다시하기·다른 판·같은 판 다시). 시계 표시는
  **재사용**하고 값만 다시 세운다 — 매번 새로 만들면 숫자가 겹쳐 쌓인다.
- ⚠️ **씬 인스턴스는 재사용된다.** 재시작하면 이전 판 오브젝트는 파괴되는데 필드는 남으므로
  `create()` 에서 `timerText` 를 **비운다**. 안 비우면 파괴된 Text 를 건드려 예외가 나고, 그 프레임에서
  루프가 끊겨 **화면이 통째로 멈춘다**(실측 2026-08-30: `setColor` → `Frame.setSize`).
- 시계는 **카운트다운(3·2·1)이 끝난 뒤** 돈다 — 코어 `startCountdown`(전 게임 공용)이 그동안 입력까지
  흡수한다. 바로 재면 판을 훑어볼 1~2초를 그냥 잃는다.
- ⚠️ 시계는 **`game.loop.rawDelta`** 로 깎는다. Phaser 의 `delta` 는 목표 FPS 로 고정된 값이라
  저사양 기기에서 실제보다 천천히 흐른다(전 게임 공통 함정).
- 시계 표시 자리는 **보드 패널 상단과 카드 사이의 빈 띠**(`boardTop`+52). depth 800 — 저작 인테리어(3)·
  암막(5)이 이 자리를 덮기 때문이다(하단 버튼과 같은 이유).
#### 제한시간은 **고정값이 아니라 사다리**다 (PO 2026-08-30)

"**5회 성공마다 5초씩** 줄이고, 최상 난이도는 **2분 30초**". 같은 시간이라도 처음 잡는 사람에게는
빠듯하고 익숙해지면 헐겁다 — 승수만큼 조여 **실력이 는 만큼 압박도 늘게** 한다.

| | 시작 | 최상까지 |
|---|---|---|
| 1장 뽑기 | **3:30**(210초) | 12단계 = **60승** |
| 3장 뽑기 | **4:00**(240초) | 18단계 = **90승** |

  사용하고 줄어드는 것도 별개로"). 그래서 **승수 카운터도 모드별**이다 — 한쪽을 많이 이겼다고
  다른 쪽이 어려워지면 안 된다.

- 홈 팝업이 **규칙(공통 한 줄) + 행마다 그 모드의 다음 단축까지 남은 승수 + 버튼의 현재 제한시간**을

### 3장 뽑기 표현 · 카드 인덱스 (2026-08-29)

- **웨이스트는 클론다이크 기본대로** 그린다 — 1장 뽑기는 한 장, 3장 뽑기는 **한 번에 뽑은 3장을 옆으로
  겹쳐** 놓고 **맨 위 한 장만 완전히 열려** 그것만 낼 수 있다(`WASTE_FAN_STEP` 48px).
  ⚠️ 겹친 카드에는 **입력을 달지 않는다** — 달면 규칙상 못 내는 카드가 눌린다.
  ⚠️ **부채꼴 기준점은 고정이다**(`wasteFanFrom` = 뽑기 직전 waste 길이). "맨 위에서 3장"으로 잡으면
  한 장 낼 때마다 남은 카드가 옆으로 **밀려오고 아래 카드가 새로 튀어나온다**(2026-08-29 신고).
  기준점을 고정해야 세 장이 제자리를 지키다가, **다 없어졌을 때 비로소 이전에 뽑아 둔 카드 한 장**이
  드러난다. 되돌리기로도 되살아나야 하므로 `history` 에 상태와 **함께** 싣는다.
- **카드 앞면은 두 배치가 따로 있다**(`scenes/cardFace.ts` `CardFaceStyle`):

  · `index` — **보너스 게임 전용**. 좌상단에 랭크 위·무늬 아래로 쌓은 모서리 인덱스.
  ⚠️ 텍스처 캐시 키에 **스타일이 들어간다**(`cardView.faceKey`) — 안 넣으면 먼저 구운 쪽 그림이
  다른 게임에도 나온다(캐시는 씬이 아니라 게임 전역).
  ⚠️ `index` 배치에서 **무늬와 중앙 랭크가 약간 겹치는 것은 허용**한다(PO 결정) — 둘 다 크게 두는
  쪽을 택했다. 그래서 "겹치면 안 된다"는 제약으로 되돌리지 말 것.

## 압축 텍스처(ASTC) 파이프라인 (2026-08-31)

WebP 는 다운로드만 줄이고 디코드 RGBA(`w×h×4`)는 그대로였다. ASTC 는 GPU 가 압축된 채로 읽어 **배경 1/9(6×6)·캐릭터 1/4(4×4)**.
실측 샘플(층·호텔·손님·카드뒷면): 6×6 SSIM 0.989~0.992, 4×4 0.997 — 육안 동일. 8×8 은 알파 경계 프린징 → 안 쓴다.

| 단계 | 어디 | 무엇 |
|---|---|---|
| 굽기 | `scripts/encode-astc.py --deploy <조립본>` (Python, `astc-encoder-py`=ARM astcenc) | 유형별 블록: 배경·층·큰 채색 패널 6×6(SSIM≥0.985, 미달 시 4×4 강등) · 캐릭터·손님 4×4(≥0.99) · **UI·카드·아이콘·텍스트·Ruin 제외**. KTX v1 로 `<key>.ktx` + `ui-assets-astc.json`{key→ktx} |
| 로드 | `assets.ts loadUpload(scene,key,path?,astcKey?)` | 표에 있으면 `load.texture({ASTC:{type:'KTX'}, IMG})` — GPU 미지원이면 IMG(WebP) 폴백. 매니페스트 일괄·부지 그룹(`assetBudget.loadKeys`)·손님 시트(`cust:Custmer_NN`)·수동 로드 전부 이 함수 |
| 게이트 | `check-texture-budget.mjs` | 표가 있으면 그 키는 ASTC 바이트로 센다(`ASTC 적용 N장` 줄) |
| 검증 | `scripts/verify-astc.mjs` | 조립본을 정적 서빙(6299)해 헤드리스에서 `source[0].compressionAlgorithm` 확인 — **SwiftShader 가 ASTC 확장을 지원**해 로컬로 끝까지 검증 가능 |

- 순서: `build:solitaire → deploy:assemble → npm run encode:astc → check:budget --deploy → vercel deploy`. 굽기 ≈2~3분(medium).
  실측(조립본, 2026-08-31): **부팅 상주 156 → 64MB · 최악 204 → 106MB** (ASTC 87장 −116MB, 매니페스트 계정) · 프로덕션 번들에서
  KTX 178장 수신·WebP 중복 0·오류 0(`npm run verify:astc`).
- ⚠️ **조립 전에 정적 검증 서버(6299)를 내릴 것** — 서버의 cwd 가 `d:/tmp/rl-deploy` 라 조립이 폴더를 못 지우고 **예전 번들이
  그대로 남는다**(실측: 두 번 연속 "KTX 0장" 의 정체). 조립 로그에 `✓ solitaire` 가 떠도 assets/ 의 타임스탬프를 볼 것.
- ⚠️ **`getSourceImage()` 는 압축 텍스처에서 null** — 크기는 `texSize(texture)`(assets.ts)로 잰다(전 파일 치환 완료). 캔버스에
  **그려야** 하는 텍스처(cardView 뒷면·간판 합성·폐건물 상단 검출)는 반드시 제외 목록(EXCLUDE_RE)에 있어야 한다 — 실제로
  customers.ts `null.width` 로 부팅이 멈췄고, Ruin 이 canvas 검출에 쓰여 제외했다.
- ⚠️ ASTC 표는 **게임 생성 전에 `fetch`** 로 받는다(main.ts `preloadAstcTable` → assets.ts 모듈 변수). Phaser 로더로 받으면 같은
  preload 안의 다른 로드보다 먼저 온다는 보장이 없고(실측: 조립본 KTX 0장·WebP 437장), 개발 서버는 없는 파일에 index.html 을
  200 으로 주어 JSON 파싱 오류로 로더가 꼬였다(부팅 정지). fetch 는 content-type 이 JSON 이 아니면 빈 표로 둔다.
- 개발 서버는 원본 PNG(표 없음) — ASTC 경로는 조립본에서만 켜진다. 개발에서 보려면 조립본의 `.ktx` + json 을 `public/` 에
  잠깐 복사(검증 후 **반드시 삭제** — 커밋 금지).
- 예산 계정(`assetBudget.measure`)은 `source[0]` 크기 × 4 로 세므로 ASTC 도 RGBA 처럼 보수적으로 잡힌다.
