# 허브 전체 게임 — 공용 서버 확장 계획

> 2026-08-18 작성 · **계획 문서. 구현하지 않는다.**
>
> 선행: `plans/pumprush-server.md`(파일럿) · 설계 `games/BobbleRunner/docs/SERVER_INTEGRATION.md`
> 플랫폼 문서: `docs/PLATFORM_INTEGRATION_DESIGN.md` · `docs/GAME_BACKEND_DESIGN.md`

---

## 0. 원칙 — 게임마다 서버를 붙이지 않는다

> **공용 층을 한 번 만들고, 게임은 그 층에 붙는다.**
> 게임 20종에 각각 인증·지갑·세이브를 구현하면 20벌의 버그와 20벌의 보안 구멍이 생긴다.

세 가지 하위 원칙:

1. **로그인은 허브에서 한 번.** 게임은 **Portal Bridge 로 토큰을 물려받는다**(이미 20게임 배선 완료).
2. **게임은 자기 상태만 안다.** 계정·지갑은 허브/서버 소유, 게임은 `/save/{game}` 네임스페이스만 쓴다.
3. **독립 실행도 유지한다.** 허브 없이 직접 URL 로 들어와도 게임이 돌아야 한다
   (`PLATFORM_INTEGRATION_DESIGN.md` 의 통합↔독립 양립).

## 2. 구조 — 3층

```
┌──────────────────────────────────────────────────────────────┐
│  허브 (games/hub)                                             │
│   · 로그인 1회(소셜+게스트) · 지갑·계정 · 글로벌 랭킹           │
│   · 게임 실행 시 Portal Bridge 로 **토큰 + 계정 컨텍스트** 전달 │
└───────────────────────────┬──────────────────────────────────┘
                            │ portalContext()  ← 이미 20게임 배선됨
┌───────────────────────────▼──────────────────────────────────┐
│  @casual/core  (공용 층 — 한 번만 만든다)                      │
│   platform 포트 · 복제본+아웃박스 · 인증 클라 · 로그인 UI 부품   │
│   local 어댑터(오프라인·독립실행) ↔ server 어댑터                │
└───────────────────────────┬──────────────────────────────────┘
                            │
┌───────────────────────────▼──────────────────────────────────┐
│  게임 20종 — 자기 상태만. `/save/{game}` 네임스페이스           │
│   T1: 개별 이관   T2: 표준 절차   T3: 일괄                     │
└──────────────────────────────────────────────────────────────┘
```

**독립 실행 경로**: 허브를 안 거치면 게임이 자체 로그인 화면을 띄운다(같은 코어 부품 재사용).
토큰만 있으면 나머지는 동일하다.

## 3. 단계

### H0. 파일럿 — 펌프러시 (`plans/pumprush-server.md`)

**목적은 펌프러시를 서버에 붙이는 게 아니라, 공용 층에 무엇이 들어가야 하는지 알아내는 것이다.**

- 펌프러시는 **가장 무거운 게임**(loadSave 107)이라 파일럿으로 적합하다 — 여기서 되면 나머지는 쉽다.
- ⛔ **H1 을 H0 완료 전에 시작하지 않는다.** 검증 안 된 것을 코어로 올리면 20게임이 같이 흔들린다.

**H0 종료 조건** — 펌프러시가 S3(복제본)·S5~S9(인증·세이브·지갑·런검증)까지 서버에서 돌고,
**어떤 코드가 게임 고유이고 어떤 코드가 공용인지 목록이 나와 있다.**

---

### H1. 공용 층 추출 — 펌프러시에서 코어로 승격

**의존** H0

**작업**
1. 복제본+아웃박스를 `@casual/core` 로 승격 — 게임별 세이브 스키마는 **제네릭**으로 받는다.
2. 인증 클라이언트(토큰 보관·갱신·만료 처리)를 코어로.
3. 로그인 화면 **부품**(소셜 버튼·게스트·충돌 택일 UI)을 코어 UI 로. *화면 조립은 게임/허브가 한다.*
4. `platform` 포트의 **server 어댑터** 구현(지금은 `local` 뿐).
5. ⚠️ **12게임 공유 사본 문제** — 코어를 고치면 전 게임이 영향을 받는다.
   `docs/` 규약(솔리테어 파일럿 이력)대로 **버전·로컬 벤더링 전략을 먼저 정한다.**

**종료 조건** — 펌프러시가 코어 공용 층만 써서 돌아간다(게임 고유 코드에 네트워크가 없다).
**롤백** — 게임은 `local` 어댑터로 되돌리면 오프라인 동작 복귀.

---

### H2. 허브 = 계정·지갑 호스트

**의존** H1

**컨텍스트** — 허브는 이미 `account.ts`·`leaderboard.ts` 를 갖고 있고 `localStorage` 38곳을 쓴다.
메모리상 **계정/경제가 store→허브로 이관**된 상태다. 즉 *역할은 이미 허브에 있고, 서버만 없다.*

**작업**
1. 허브 로그인 화면(소셜+게스트) — H1 부품 조립.
2. 허브 지갑·계정을 서버 권위로.
3. **Portal Bridge 확장** — `portalContext()` 가 **세션 토큰**을 함께 전달.
   ⚠️ 토큰을 URL 쿼리로 넘기지 않는다(로그·히스토리 유출). `postMessage`/`sessionStorage` 등 안전 경로.
4. 게임 진입 시 토큰 검증 실패 → 게임의 자체 로그인 경로로 폴백.

**종료 조건** — 허브에서 로그인 → 게임 진입 시 **재로그인 없이** 서버 세션이 이어진다.

### H3. T1 게임 개별 이관 (4종)

**의존** H1 · H2 · **각 게임 병렬 가능**

| 게임 | 규모 | 특이사항 |
|---|---|---|
| Solitare | loadSave 100 · localStorage 42 | 펌프러시와 **거의 같은 모양** — 절차 재사용률 최고 |
| SocialCasino | localStorage 88 | 자체 `save.ts` 없이 흩어져 있다 → **먼저 한 모듈로 모으는 선행 작업 필요** |
| Homerun | localStorage 33 | 동일 |
| (BobbleRunner) | — | H0 에서 완료 |

⚠️ **SocialCasino·Homerun 은 "세이브 모듈 추출" 이 선행**이다. 흩어진 `localStorage` 호출을
한 모듈로 모으지 않으면 복제본 구조를 넣을 자리가 없다. 이건 **서버와 무관한 리팩터링**이라
H1 을 기다리지 않고 먼저 해도 된다.

### H4. T2 게임 표준 절차 (5종)

**의존** H3 에서 절차가 다듬어진 뒤

Grillking · TICTACTOE · Archery · ZombieArrow · DragonBeat.
게임당 상태가 작아 **§4 체크리스트만으로** 진행 가능해야 한다. 여기서 체크리스트가 안 통하면
절차가 덜 여문 것이니 H3 로 돌아간다.

여러 게임을 한 PR 에 묶어도 된다 — 단 게임당 검증은 따로 한다.

## 4. 게임당 표준 이관 체크리스트 ★ 진입점

**T2·T3 는 이 체크리스트만으로 착수한다.** 새로 설계하지 않는다.

```
□ 1. 저장 상태 목록화 — 무엇을 저장하나? (필드 나열)
□ 2. 권위 분류 — 각 필드에 S/V/M/C 등급 부여
     S=서버권위(재화·소유) V=서버검증(기록) M=단조병합(최고기록) C=기기(설정)
□ 3. 세이브 모듈 단일화 — localStorage 직접 호출이 여러 곳이면 한 모듈로 모은다(선행)
□ 4. 코어 복제본+아웃박스 어댑터로 교체 — 동기 API 유지
□ 5. 검증: 오프라인·비로그인에서 **동작 무변경** ← 이게 통과 안 되면 되돌린다
□ 6. Portal 토큰 수신 배선 + 독립 실행 폴백
□ 7. `/save/{game}` 연결 + 필드별 병합
□ 8. (재화가 있으면) 지갑을 서버 grant 파이프로
□ 9. 게임 테스트 전체 통과 + 헤드리스 부팅 에러 0
```

**게임당 예상**: T3 ≈ 0.5일 · T2 ≈ 1~2일 · T1 ≈ 1~2주(SocialCasino 는 선행 리팩터 별도).

## 5. 열린 결정

### 5-1. 재화를 게임 간 공유할 것인가

`PLATFORM_INTEGRATION_DESIGN.md` 가 "공유↔격리 양립"을 다룬다. **지금 정해야 한다** —
지갑 스키마가 갈린다.

| 안 | 뜻 | 영향 |
|---|---|---|
| 완전 공유 | 코인 하나로 전 게임 | 게임별 경제 밸런스가 서로를 오염시킨다 |
| 완전 격리 | 게임마다 지갑 | 허브 리워드 플랫폼(CashPOP) 구상과 어긋난다 |
| **하이브리드** | 게임 재화는 격리, **플랫폼 재화(젬·리워드)는 공유** | 권고 — 밸런스 독립 + 크로스 프로모션 양립 |

### 5-2. TICTACTOE 백엔드 — 통합 vs 병존

실시간 대전이 이미 **Vercel+Supabase**(`services/api`)에 서 있다. 계정·지갑만 새 백엔드로 옮기고
실시간은 그대로 둘지, 전부 이관할지. **권고: 병존.** 실시간 판정을 옮기는 비용 대비 이득이 작다.

### 5-3. 코어 변경의 폭발 반경

코어는 **12게임이 공유**한다. H1 에서 코어를 크게 바꾸면 전 게임 회귀 위험이 있다.
버전 고정·게임별 점진 채택 전략을 H1 착수 시 확정한다.

## 7. 요약

- **20게임이 아니라 실질 4~9게임의 문제다** — 절반 이상이 저장할 상태가 거의 없다.
- **Portal Bridge 가 이미 20게임에 깔려 있다** — 허브 로그인 → 게임 토큰 전달 통로가 공짜로 있다.
- 순서는 **파일럿(펌프러시) → 공용 층 추출 → 허브 계정 → T1 → T2 → T3**.
  검증 안 된 것을 코어로 올리면 20게임이 함께 흔들린다.
- 지금 당장 서버 없이 할 수 있는 일이 둘 있다: **펌프러시 S3**, **SocialCasino·Homerun 세이브 모듈 추출**.
